When Apple processed the purchase as a sandbox purchase (TestFlight, App Review or Xcode) but the request used a live key, the transaction is saved in Live as a test purchase and the response carries `"is_test_purchase": true` along with the existing `environment_mismatch` warning.

If the StoreKit transaction id already belongs to a different project, the request is rejected with `409` and `{"error": "storekit_transaction_id_conflict", "message": "This StoreKit transaction id already belongs to a different project."}`. Nothing is saved. Check that the app is using the publishable key of the project the purchase belongs to.

## Bundle id mismatch (400)

The JWS is signed by Apple and carries the `bundleId` of the app that made the purchase. ZeroSettle compares it with the bundle id registered for your app in the dashboard. If they differ, the request is refused with `400`:

```json
{
  "error": "The transaction's bundle id does not belong to this app.",
  "code": "bundle_id_mismatch"
}
```

Nothing is saved. This check has been enforced in production since 2026-10-25.

What to do:

- Almost always the bundle id registered in the dashboard (App settings) is wrong or missing a variant. Fix it there, then the next sync succeeds. Do not change the app's bundle id.
- A project with no registered bundle id is never refused.
- Accepted without extra setup: the exact registered id, its `maccatalyst.` form, and the registered id plus `.watchkitapp` or `.watchkitextension`. Any other extension or sibling app id counts as a mismatch.
- The SDK keeps the transaction unfinished and retries, so purchases are not lost while you fix the registration.

Other `400` errors are `Invalid JSON body`, `jws_representation is required`, `user_id is required` and `Missing productId in JWS payload`. A JWS that fails Apple signature verification returns `401` with `JWS signature verification failed`.

## Another user owns the subscription

If the Apple subscription already belongs to a different `user_id`, the call returns `200` with `"owned": false`, `"conflict": true` and `"claim_available": true`. Nothing is granted. Offer [Claim Entitlement](/api-reference/endpoint/claim-entitlement) if the person should take it over.

## Bulk reconcile

When the body has a `transactions` array instead of `jws_representation`, the request reconciles subscription state for `user_id`. Each entry carries `signed_transaction` and, optionally, `signed_renewal_info`. The response is `{"status": "ok", "processed": n, "events_emitted": n, "skipped": [{"reason": "...", "transaction_id": "..."}]}`.

Only the newest entry for each original transaction id is processed. Each entry updates the entitlement row for its own product, so after a crossgrade the old plan is not revived.

Skip reasons:

- `jws_verification_failed`: the signed payload did not verify.
- `app_account_token_mismatch`: the transaction's app account token does not belong to the request `user_id`.
- `environment_mismatch`: the transaction's environment does not match the request key.
- `cross_user_otid_skipped`: no row for this user has that original transaction id.
- `product_row_missing`: the user has rows for that original transaction id, but none for the transaction's product. This can happen briefly during a crossgrade, before the new product's sync lands. It clears on the next reconcile.
- `stale_signed_date`: the renewal info is older than what is already stored.
