## SDK 1.2.4 — `Identity` enum, `userId`-less methods

ZeroSettleKit 1.2.4 introduces a type-safe `Identity` enum and `ZeroSettle.shared.identify(_ identity:)` as the canonical entry point for declaring the active user. Once you've identified, every user-scoped method on `ZeroSettle.shared` reads from the declared identity — you no longer need to pass `userId` on each call.

```swift
public enum Identity {
    case user(id: String, name: String? = nil, email: String? = nil)
    case anonymous
    case deferred
}
```

`bootstrap(userId:name:email:)` is deprecated in this release. It still compiles and routes to `identify(.user(id:))` for source compat. It will be removed in **ZeroSettleKit 2.0**.

### Why this matters

Before 1.2.4, several public methods (most notably `fetchProducts(userId:)`) accepted a `userId` parameter but did **not** propagate it to the StoreKit transaction listener. Calling `configure()` followed by `fetchProducts(userId:)` would create a backend `Identity` for the user, but any subsequent StoreKit purchase would arrive on the listener with no `userId` set and would be silently left unfinished — never reaching the backend, never appearing on the dashboard.

`identify(_:)` is the single source of truth: it sets `currentUserId`, propagates it to the StoreKit listener, syncs any pending transactions, fetches the catalog, and restores entitlements. The enum surface adds something the string-based API couldn't express: explicit declarations of `.anonymous` (guest sessions with stable persisted UUIDs) and `.deferred` (auth resolves on a later screen — suppress the no-user warning). Both are first-class, type-checked alternatives to "skip identify entirely," which was the silent failure mode the 1.2.4 work set out to eliminate.

### Migration in two lines

Before:
```swift
ZeroSettle.shared.configure(.init(publishableKey: "..."))
try await ZeroSettle.shared.bootstrap(userId: user.id)
let entitlements = try await ZeroSettle.shared.restoreEntitlements(userId: user.id)
try await ZeroSettle.shared.cancelSubscription(productId: "premium", userId: user.id)
```

After:
```swift
ZeroSettle.shared.configure(.init(publishableKey: "..."))
try await ZeroSettle.shared.identify(.user(id: user.id))
let entitlements = try await ZeroSettle.shared.restoreEntitlements()
try await ZeroSettle.shared.cancelSubscription(productId: "premium")
```

### Anonymous and deferred identity

If your app supports guest purchases or resolves auth on a later screen, declare that intent explicitly:

```swift
// Guest session — stable UUID across launches, cleared on logout()
try await ZeroSettle.shared.identify(.anonymous)

// Auth on a later screen — suppresses the "no user identified" warning
try await ZeroSettle.shared.identify(.deferred)
// ...later, when the user logs in:
try await ZeroSettle.shared.identify(.user(id: user.id))
```

Reconciliation of anonymous purchases into an authenticated account (i.e. "the user logged in after making a guest purchase — keep their entitlements") will land in a follow-up release as `completeIdentification(.user(...))`. PR C v1 ships the SDK enum surface only.

`fetchProducts(userId:)` and `purchaseViaStoreKit(productId:userId:)` keep their existing optional-`userId` signatures (no deprecation), but now fall back to the identified user when called without one — so `ZeroSettle.shared.fetchProducts()` after `identify(_:)` returns the user-context catalog automatically.

## When to Use What

Not sure which view or manager to use? Here's the decision tree:

### Drop-in Views (Zero Custom UI)

| View | Use When |
|---|---|
| **`MigrationTipView`** | You only need StoreKit-to-web migration offers |
| **`OfferTipView`** | You want migration + upgrade offers from a single component (recommended for new integrations) |

Both views have identical init signatures and placement patterns. `OfferTipView` is the superset — it handles everything `MigrationTipView` does, plus upgrade offers.

### Custom UI (Headless Managers)

| Manager | Use When |
|---|---|
| **`ZSMigrationManager`** | You're building custom migration-only UI |
| **`ZSOfferManager`** | You're building custom UI that handles migration + upgrades (recommended for new integrations) |

### Modal Sheets

| Modifier | Use When |
|---|---|
| **`.upgradeOffer()`** | You want a full-screen modal upgrade offer |
| **`.cancelFlow()`** | You want a cancel flow with survey + retention offers |
| **`.retentionSheet()`** | You want the legacy subscription management sheet |

<Note>
  `MigrationTipView` and `ZSMigrationManager` are **not deprecated**. They continue to work and are actively maintained.
  `OfferTipView` and `ZSOfferManager` are the recommended path forward for new integrations because they handle
  more flow types from a single component.
</Note>
