ZeroSettle works alongside Google Play Billing. You can use web checkout as your primary payment method and Play Billing as a fallback, or offer both options side-by-side.

## How It Works

When `syncPlayPurchases` is enabled (the default), the SDK automatically:

1. Installs a `PurchasesUpdatedListener` and connects to Google Play Billing
2. Forwards every completed Play purchase to your ZeroSettle backend (`POST /v1/iap/play-store-transactions/`)
3. Merges Play Store entitlements with web checkout entitlements
4. Acknowledges purchases per the [acknowledgement model](/sdk/android/acknowledgement-model), retrying failed syncs via a [persistent sync queue](/sdk/android/sync-queue)

This means a user who purchases via the Play Store will have their entitlements available via `ZeroSettle.entitlements` — alongside their web checkout purchases.

## Configuration

Play purchase sync is enabled by default:

```kotlin
import com.zerosettle.sdk.ZeroSettle
import com.zerosettle.sdk.ZeroSettleConfig

// Play purchase sync enabled (default)
ZeroSettle.configure(context, ZeroSettleConfig(
    publishableKey = "zs_pk_live_…"
))

// Play purchase sync disabled (use with RevenueCat)
ZeroSettle.configure(context, ZeroSettleConfig(
    publishableKey = "zs_pk_live_…",
    syncPlayPurchases = false
))
```

<Warning>
  If you use RevenueCat, set `syncPlayPurchases = false` to avoid conflicts. RevenueCat manages its own Play Billing listener. See [RevenueCat Integration](/iap/revenuecat-integration).
</Warning>

## User Choice Billing

If your app and market are enrolled in Google's **User Choice Billing (UCB)**, the SDK exposes a `StateFlow` you can use to adapt your purchase UI:

```kotlin
ZeroSettle.isUcbEnabled.collect { ucbEnabled ->
    // ucbEnabled reflects the server-side PlayBillingConfig.is_enabled.
    // true  → present a single unified "Buy" button; Google's choice screen
    //         routes the purchase between web checkout and Play Billing.
    // false → you may show separate web and Play purchase paths.
}
```

`isUcbEnabled` is tenant- and market-scoped — it resets on `configure()`, not on `logout()`, and starts `false` until `identify()` completes bootstrap.

## Purchasing via Play Billing

Use `purchaseViaPlayBilling()` to trigger a native Play Billing purchase. Like `purchase()`, it is awaitable and returns a `Result<CheckoutTransaction>`. Requires `syncPlayPurchases = true`.

```kotlin
val result = ZeroSettle.purchaseViaPlayBilling(
    activity = this,
    productId = "premium_monthly",
)
result
    .onSuccess { txn -> /* unlock content */ }
    .onFailure { e ->
        when (e) {
            is ZeroSettleError.PurchaseCancelled -> { /* user cancelled */ }
            is ZeroSettleError.ProductNotFound -> showError("Product not in catalog")
            is ZeroSettleError.PlayBillingError ->
                showError("Play error ${e.responseCode}: ${e.debugMessage}")
            is ZeroSettleError.PurchasePending -> { /* pending Google review */ }
            else -> showError("Purchase error: ${e.message}")
        }
    }
```

## Hybrid Purchase Flow

A common pattern is to offer web checkout as the primary option with Play Billing as a fallback:

```kotlin
@Composable
fun ProductView(product: Product) {
    val scope = rememberCoroutineScope()
    val activity = LocalContext.current as Activity

    Column(verticalArrangement = Arrangement.spacedBy(12.dp)) {
        // Primary: Web checkout (lower fees)
        Button(onClick = {
            scope.launch { ZeroSettle.purchase(activity, product.id) }
        }) {
            Text("Buy")
        }

        // Fallback: Play Billing (if the product is configured in Play Console)
        if (product.playProductId != null) {
            OutlinedButton(onClick = {
                scope.launch { ZeroSettle.purchaseViaPlayBilling(activity, product.id) }
            }) {
                Text("Buy with Google Play")
            }
        }
    }
}
```

The `Product` model carries Play-specific fields (all nullable, populated when the product is configured in Google Play Console):
- `product.playProductId` — the Play Console product id
- `product.playBasePlanId` — the Play base plan id (subscriptions)
- `product.playStorePrice` — a forward-compat slot for the Play price (the backend does not currently emit it)

## Sync Events

When `syncPlayPurchases` is enabled, the SDK syncs Play purchases automatically. Observe sync outcomes via `ZeroSettle.events` — there is no delegate interface on Android:

```kotlin
ZeroSettle.events.collect { event ->
    when (event) {
        is ZeroSettleEvent.SyncFailed ->
            // A Play sync failed. terminal == true means the retry schedule
            // is exhausted. The purchase itself still went through Google.
            println("Sync failed (terminal=${event.terminal}, attempts=${event.attempts})")
        is ZeroSettleEvent.EntitlementsRefreshed -> { /* entitlements updated */ }
        else -> Unit
    }
}
```

<Note>
  Sync failures don't affect the Play purchase itself. The user still gets their purchase through Google. The sync is retried automatically via the [persistent sync queue](/sdk/android/sync-queue).
</Note>

## Entitlement Sources

Entitlements track where each purchase came from:

```kotlin
val entitlements = ZeroSettle.restoreEntitlements().getOrThrow()

for (entitlement in entitlements) {
    when (entitlement.source) {
        EntitlementSource.WEB_CHECKOUT ->
            println("${entitlement.productId}: purchased via ZeroSettle")
        EntitlementSource.PLAY_STORE ->
            println("${entitlement.productId}: purchased via Google Play")
        EntitlementSource.STORE_KIT ->
            println("${entitlement.productId}: purchased via App Store")
        EntitlementSource.UNKNOWN ->
            println("${entitlement.productId}: unknown source")
    }
}
```

Both sources are merged into a single entitlements list. Your app doesn't need to treat them differently.

## Cross-account ownership conflicts

If a Play purchase is already owned by a different ZeroSettle account, the SDK does **not** silently transfer it. It surfaces a `PendingClaim` on `ZeroSettle.pendingClaims`; the host app resolves it explicitly with `ZeroSettle.transferPlayOwnershipToCurrentUser(productId)`.
