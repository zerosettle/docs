## SDK 1.2.4 — `identify()` and `userId`-less methods

ZeroSettleKit 1.2.4 introduces `ZeroSettle.shared.identify(userId:name:email:)` as the canonical entry point for setting the active user. Once you've identified, every user-scoped method on `ZeroSettle.shared` reads from the identified user — you no longer need to pass `userId` on each call.

The legacy `userId`-accepting overloads still compile and work in 1.x. They emit a `@available(deprecated)` warning at the call site and will be removed in **ZeroSettleKit 2.0**.

### Why this matters

Before 1.2.4, several public methods (most notably `fetchProducts(userId:)`) accepted a `userId` parameter but did **not** propagate it to the StoreKit transaction listener. Calling `configure()` followed by `fetchProducts(userId:)` would create a backend `Identity` for the user, but any subsequent StoreKit purchase would arrive on the listener with no `userId` set and would be silently left unfinished — never reaching the backend, never appearing on the dashboard.

`identify()` is the single source of truth: it sets `currentUserId`, propagates it to the StoreKit listener, syncs any pending transactions, fetches the catalog, and restores entitlements. The deprecation pushes every integration onto the safe path.

### Replacement table

| Deprecated | Replacement (after `identify()`) |
|---|---|

| `migrationManager(for:stripeCustomerId:)` | `migrationManager(stripeCustomerId:)` |
| `offerManager(for:stripeCustomerId:)` | `offerManager(stripeCustomerId:)` |
| `cancelSubscription(productId:userId:immediate:)` | `cancelSubscription(productId:immediate:)` |

| `pauseSubscription(productId:userId:pauseDurationDays:)` | `pauseSubscription(productId:pauseDurationDays:)` |

### Migration in two lines

Before:
```swift
ZeroSettle.shared.configure(.init(publishableKey: "..."))
try await ZeroSettle.shared.bootstrap(userId: user.id)
let entitlements = try await ZeroSettle.shared.restoreEntitlements(userId: user.id)
try await ZeroSettle.shared.cancelSubscription(productId: "premium", userId: user.id)
```

After:
```swift
ZeroSettle.shared.configure(.init(publishableKey: "..."))
try await ZeroSettle.shared.identify(userId: user.id)
let entitlements = try await ZeroSettle.shared.restoreEntitlements()
try await ZeroSettle.shared.cancelSubscription(productId: "premium")
```

`fetchProducts(userId:)` and `purchaseViaStoreKit(productId:userId:)` keep their existing optional-`userId` signatures (no deprecation), but now fall back to the identified user when called without one — so `ZeroSettle.shared.fetchProducts()` after `identify()` returns the user-context catalog automatically.

## Parameter Removals

| Deprecated Parameter | Affected APIs | Notes |
|---|---|---|
| `freeTrialDays` | `CheckoutSheet.init`, `.checkoutSheet(...)`, `preload()`, `warmUp()`, `warmUpAll()` | Free trial days are now auto-computed from the product's configured trial. Remove the parameter — it is ignored. |
| `onDismiss` on `MigrationTipView` | `MigrationTipView.init(onDismiss:)` | Use `init(onEvent:)` instead. `onDismiss` maps to the `.dismissed` event only. |

## Property Deprecations

| Deprecated | Current | Notes |
|---|---|---|
| `ZeroSettle.shared.migrationManager` | `ZeroSettle.shared.offerManager(for:stripeCustomerId:)` | `offerManager` handles migration + upgrades |

## When to Use What

Not sure which view or manager to use? Here's the decision tree:

### Drop-in Views (Zero Custom UI)

| View | Use When |
|---|---|
| **`MigrationTipView`** | You only need StoreKit-to-web migration offers |
| **`OfferTipView`** | You want migration + upgrade offers from a single component (recommended for new integrations) |

Both views have identical init signatures and placement patterns. `OfferTipView` is the superset — it handles everything `MigrationTipView` does, plus upgrade offers.

### Custom UI (Headless Managers)

| Manager | Use When |
|---|---|
| **`ZSMigrationManager`** | You're building custom migration-only UI |
| **`ZSOfferManager`** | You're building custom UI that handles migration + upgrades (recommended for new integrations) |

### Modal Sheets

| Modifier | Use When |
|---|---|
| **`.upgradeOffer()`** | You want a full-screen modal upgrade offer |
| **`.cancelFlow()`** | You want a cancel flow with survey + retention offers |
| **`.retentionSheet()`** | You want the legacy subscription management sheet |

<Note>
  `MigrationTipView` and `ZSMigrationManager` are **not deprecated**. They continue to work and are actively maintained.
  `OfferTipView` and `ZSOfferManager` are the recommended path forward for new integrations because they handle
  more flow types from a single component.
</Note>
