## October 2026

<Update label="Platform" description="Unreleased">
### Guest to account: move a guest's purchases onto their account

Your server can now tell ZeroSettle that a guest id and an account id are the same person, and ZeroSettle moves the purchases, purchased credits, analytics and experiment rows across. It is one way, refuses (and moves nothing) when both sides hold a live entitlement to the same non-consumable product, and never cancels anything in Stripe or a store. The old id keeps resolving to the account. See [Guest to Account](/iap/guest-to-account).

**New endpoints** (additive):
- `POST /v1/identities/reconcile/`, with your secret key and an `Idempotency-Key`. Limits: 300 a minute and 50,000 a day per project.
- `POST /v1/identities/link-token/`, which mints a short-lived token for the app to present.
- `POST /v1/iap/identities/reconcile/`, which the SDK calls with a link token.
- `POST /v1/iap/identity-link/`, which moves a guest's experiment and analytics rows to the signed-in id with the publishable key and never moves purchases (unless it is sent a link token).

**New webhook:** `identity.reconciled`, sent on every merge, including one that moved nothing. Its `data` has `reconciliation_id`, `from_user_id`, `into_user_id`, `actor` and `moved`, and **no `external_user_id`**. If you subscribe to `*`, make sure your handler branches on `type` before it reads `data.external_user_id`. See [Event Webhooks](/iap/event-webhooks#identity-reconciled).

**Changed: `POST /v1/iap/restore-purchases/`.** The request shape is the same. A restore that would put two live entitlements to the same non-consumable product on one user now restores nothing from that guest and answers `200` with `restored: 0` and a message to contact support. `target_identity_id` is an integer when a guest matched. A restore now sends `identity.reconciled` instead of `subscription.purchased`, and the endpoint is rate limited: over a limit it returns `429` with `Retry-After`, so a restore button should treat a `429` as a failed restore.

**Changed: paywall events before `identify`.** Events now carry a per-device id instead of the literal `anonymous`, and iOS events include the StoreKit environment. Counts of app users and paywall viewers can rise as apps update.

**SDKs (next release of each):**
- iOS: `currentUserId` is public (read-only), new `analyticsUserId`, `reconcile(linkToken:)` returning `ReconcileResult` (with `switchedToAccount`), and new `ZeroSettleError` cases `reconcileRefused`, `invalidLinkToken` and `rateLimited(retryAfter:)`. Apps that switch exhaustively over `ZeroSettleError` need the new cases or a `default`.
- Android: `trackEvent` (new), `analyticsUserId()`, `reconcile(linkToken)` returning `Result<ReconcileResult>`, and new `ZeroSettleError` cases `ReconcileRefused`, `InvalidLinkToken` and `RateLimited`.
- Flutter (iOS and Android): `analyticsUserId()` and `reconcile(linkToken:)`. `trackEvent` already existed; on Android the bridge now sends events instead of dropping them.
- All: `identify(.user)` logs a warning when one signed-in user replaces another without `logout()`.
</Update>

<Update label="Docs" description="2026-10-26">
### Documentation corrections

We checked these docs against the live API and the released SDKs (iOS 1.6.2, Android 1.2.1, Flutter 1.7.0) and corrected what was wrong. If you built against the old pages, check these:

- **API reference shapes.** `GET /v1/iap/products/` returns its settings in a `config` object. Transaction history reports `completed` (not `succeeded`), reports disputed payments as `refunded`, and leaves out abandoned checkouts. Entitlements use `product_type` values `consumable`, `non_consumable`, `non_renewing` and `auto_renewable`. The checkout, cancel-flow, upgrade-offer and event-tracking schemas now match what the API sends and accepts. See the [API reference](/api-reference/introduction).
- **Trailing slashes.** Every endpoint path ends in `/`. A `POST` without it is redirected and loses its body.
- **Event webhooks.** The retry schedule, `X-ZeroSettle-Event-Id` (one id per delivery) and the `migration.*` envelope are corrected. Consumable purchases send no event. See [Event webhooks](/iap/event-webhooks).
- **Android checkout return.** The Android SDK returns to `zerosettle://checkout/return`. The App Links setup previously shown on [Universal links](/iap/universal-links) was wrong.
- **TestFlight and test purchases.** A TestFlight, Xcode or App Review purchase made with a live key stays in Live, marked as a test purchase. See [Testing](/iap/testing).
- **Going live.** New accounts are approved for live web checkout by ZeroSettle; until then live checkout returns `not_whitelisted`. See [Go live](/iap/go-live).
- **Samples and requirements.** Kotlin, Flutter and React Native samples now match the released SDKs, and requirements are listed once on [SDK versions](/iap/sdk-versions). The React Native package is not published yet.
- **New pages.** [Google Play setup](/iap/google-play-setup), [Connect the App Store](/iap/connect-app-store), and a keys and environments section in [Account setup](/iap/account-setup).
</Update>

<Update label="Platform" description="2026-10-25">
### StoreKit sync checks the bundle ID

`POST /v1/iap/storekit-transactions/` now verifies the full Apple certificate chain and refuses a transaction whose bundle ID doesn't match the app's registered bundle ID, with `400` and `code: "bundle_id_mismatch"`. The SDK keeps such a transaction unfinished and retries it, so the fix is to register the right bundle ID for your app in the dashboard. Apps with no registered bundle ID are not checked. Xcode StoreKit Testing and test purchases are unaffected. See [Sync StoreKit transaction](/api-reference/endpoint/sync-storekit-transaction).
</Update>

<Update label="Platform" description="2026-10-20">
### Google Play: purchases of unlinked one-time products are recorded, not granted

A Google Play one-time purchase of a product that isn't linked to your ZeroSettle catalog used to be treated as a non-consumable, so a consumable pack could become permanent access. It is now recorded with its revenue and grants nothing until you link the product, then finishes on its own: a non-consumable grants access to each buyer and a consumable needs nothing more.

`POST /v1/iap/play-store-transactions/` for such a purchase now answers `owned: true` with `entitlement_id` null, where it could answer `owned: false` before. The response shape is unchanged. See [Google Play billing](/iap/play-billing-integration).
</Update>

<Update label="Platform" description="2026-10-16">
### StoreKit reconcile matches the right plan

Bulk reconcile on `POST /v1/iap/storekit-transactions/` now matches each entry to the entitlement row for its own product. After a crossgrade, the old plan is no longer revived. The server also checks the app account token against the request `user_id`.

The `skipped[].reason` field gains `product_row_missing` (no row for that product yet) and you may now see `app_account_token_mismatch`. The response shape is unchanged, and the full list of reasons is on the Sync StoreKit Transaction page.
</Update>

<Update label="Platform" description="2026-10-15">
### Transaction history no longer returns abandoned checkouts

`GET /v1/iap/transaction-history/` now leaves out checkout attempts that were replaced by a newer attempt before payment (internal status `superseded`). Older SDK versions showed these rows as failed purchases. Completed, pending, processing, failed and refunded transactions are returned as before, and the response shape is unchanged.

Nothing changes for SDK clients except that the list is shorter and more accurate.
</Update>

<Update label="Platform" description="2026-10-12">
### Test purchases: TestFlight and App Review purchases no longer count as revenue

A purchase Apple processes as a sandbox purchase (TestFlight, App Review, Xcode) but that your app sends with a live ZeroSettle key is now saved in Live and marked as a **test purchase**. It still grants access, so reviewers and testers are never locked out, but it is left out of revenue, MRR, subscriber counts, charts and reports unless you turn on **Include test purchases** in the dashboard.

- **`is_test_purchase`** — new boolean on each entry of `GET /v1/iap/entitlements/`, on the `POST /v1/iap/storekit-transactions/` response, and on lifecycle webhook payloads as `data.is_test_purchase`. Additive: existing integrations keep working.
- **`409 storekit_transaction_id_conflict`** — `POST /v1/iap/storekit-transactions/` now returns this when the StoreKit transaction id already belongs to a different project. Nothing is saved. New response code on an existing endpoint; successful requests are unchanged.
- **Past purchases** — purchases already flagged with an environment mismatch since 2026-04-13 are marked too. Earlier ones cannot be classified.

Nothing changes for SDK clients. See [Entitlements](/iap/webhooks) and [Event Webhooks](/iap/event-webhooks).
</Update>

<Update label="Platform" description="2026-10-07">
### Webhook accuracy: sources, refunds and billing problems

Event webhooks now report subscription state more precisely. See [Event Webhooks](/iap/event-webhooks).

- **`data.source` reports the rail** — `web_checkout`, `store_kit` or `play_store`. It is now also set on `subscription.cancelled` and `subscription.expired`, where it could previously be `null`. `admin` and `system` never appear in this field.
- **No repeated events** — one cancellation produces one `subscription.cancelled`, and one expiry produces one `subscription.expired`, even when more than one system reports the same change.
- **Renewals** — `subscription.renewed` carries the new period's `expires_at`. After a failed payment you also receive `subscription.recovered`; treat both as "grant access" and do not depend on their order.
- **Billing problems** — on web checkout the status is `past_due` and the customer keeps access while Stripe retries. On the App Store the status is `grace_period` when Billing Grace Period is enabled for the app, and `past_due` otherwise.
- **Refunds** — a full refund of the current billing period ends the subscription and sends `subscription.expired` and `transaction.refunded`. A partial refund, or a refund of an earlier period, sends only `transaction.refunded` and leaves the subscription active.
</Update>

<Update label="SDK" description="2026-08-19">
### Observer mode: track StoreKit purchases without moving checkout

**ZeroSettleKit 1.6.0** is an additive minor for apps that use ZeroSettle to instrument purchases rather than to sell them. `Configuration` is unchanged, so upgrading from 1.5.x is drop-in.

- **`recordStoreKitPurchase(_:)`** — optionally report a StoreKit purchase your own code made with `Product.purchase()`. Most apps never need it: SDK-driven purchases already sync, and renewals, refunds, and revocations arrive through the listener regardless. It exists because Apple does not redeliver a transaction `purchase()` already returned, so an app owning its paywall would otherwise wait for the next `identify(_:)`.
- **Privacy manifest** — the SDK now ships `PrivacyInfo.xcprivacy`, so you no longer declare our `UserDefaults` use or data collection on our behalf.
- **`Equatable` errors** — `ZeroSettleError` and `CheckoutFailureReason` conform, so `error == .cancelled` compiles. Prefer `isCancellation(_:)`, which also catches `CancellationError` and StoreKit's own cancel.
- **`objectWillChange` fix** — `products`, `pendingCheckout`, `isConfigured`, and `currentOffer` now notify `ObservableObject` consumers. Views bound with `@ObservedObject` that appeared static may begin re-rendering; `@Observable` consumers were never affected.

New guide: [Analytics-Only Integration](/iap/analytics-only) — using ZeroSettle purely to track purchases, trials, and entitlements, with no web checkout.

Requires **Xcode 16.3+** (`Package.swift` is `swift-tools-version: 6.1`).
</Update>

## June 2026

<Update label="SDK" description="2026-06-10">
### Automatic Apple external-purchase token minting

ZeroSettleKit now mints the Apple external-purchase token automatically at checkout initiation — no StoreKit code required from the app. Minting is region-gated (EU/EEA under the DMA alternative terms, EEA music streaming, and Japan MSCA on iOS 26.4+) and degrades gracefully: if a token cannot be minted, checkout proceeds and the transaction is recorded as token-less in the coverage dashboard.

- **Auto-minting** — the SDK resolves the eligible regime from the device's App Store storefront and mints the appropriate token type internally. The existing manual `external_purchase_token` parameter remains as an advanced override.
- **True storefront reporting** — checkout initiation now sends the device's actual App Store storefront, so jurisdiction detection for compliance reporting keys off the user's store region instead of their card billing country.
- **New setup guide** — see [External Purchase Reporting](/iap/external-purchase-reporting) for Apple program enrollment, entitlements, `SKExternalPurchase*` keys, dashboard configuration, and Google Play alternative billing setup.

Available in **ZeroSettleKit 1.5.2** (SPM + CocoaPods) and **Flutter `zerosettle` 1.7.0** (which raises its native floors to ZeroSettleKit 1.5.2 and zerosettle-android 1.2.1 — no Dart-side changes required).
</Update>

<Update label="API" description="2026-06-08">
### Trial mode: `trial` facts object + `intent_type`/`charge_amount` discriminators

Three additive, non-breaking changes to the IAP API surface the payment mechanics for free, paid, and authorization-hold trial modes. SDKs that do not yet read these fields continue to work unchanged (unknown keys are ignored).

**`GET /v1/iap/products/` — `trial` object on eligible subscription products**

When `user_id` is included in the request and the user is eligible for a trial on an `auto_renewable_subscription`, that product now carries a `trial` object:

```json
"trial": {
  "mode": "free | paid | auth_hold",
  "duration": "1_week",
  "upfront_amount_cents": 0,
  "hold_amount_cents": 0,
  "validates_card": false
}
```

- `free` — card saved, no immediate charge, billed at trial end.
- `paid` — `upfront_amount_cents` charged immediately and kept; full price billed at trial end.
- `auth_hold` — `hold_amount_cents` placed as a temporary pending authorization; released on convert or cancel.

`validates_card` is `true` for `paid` and `auth_hold`. The object is absent for non-subscription products, products without a trial, and anonymous requests.

**These are facts for the app to render its own copy — ZeroSettle ships no trial copy strings.**

**`GET /v1/iap/checkout-config/{transaction_id}/` — `intent_type` + `charge_amount`**

- `intent_type` (`"setup" | "payment"`) — which Stripe confirm method the SDK must call. `setup` for free-trial SetupIntents; `payment` for paid/auth-hold upfront charges and all normal checkouts.
- `charge_amount` (integer cents) — the amount the intent will charge or hold (`upfront_amount_cents` for paid, `hold_amount_cents` for auth-hold, normal price otherwise).

**`POST /v1/iap/payment-intents/{transaction_id}/finalize/` — `intent_type`**

Same `"setup" | "payment"` discriminator returned on finalize so the SDK can call the correct confirm method.
</Update>

<Update label="API" description="2026-06-04">
### Idle checkout sessions auto-recover instead of failing

A web checkout session that sat idle past its 30-minute validity window used to fail with `checkout_config_expired` when the buyer finally tapped Pay, forcing a full checkout restart. The backend now transparently revalidates and refreshes an expired session at payment time and proceeds — no restart, no SDK changes.

- The buyer is always charged the **exact price the checkout sheet displayed** (the amount is never silently re-resolved).
- Switch & Save migration and upgrade sessions are revalidated against the customer's current subscription before recovering. If the underlying subscription has since ended, the session still returns `checkout_config_expired` so the SDK re-evaluates eligibility — preventing a mis-aligned trial.
- No request or response schema changes; existing SDK integrations benefit automatically.
</Update>

## April 2026

<Update label="API" description="2026-04-27">
### Migration trial-end resolution moved server-side

The Switch & Save migration flow no longer sources the Stripe `trial_end` from the SDK's reported `storekit_subscription_end`. The backend now resolves it directly from Apple's App Store Server API (with a fallback to the server-stored, JWS-verified entitlement expiry). Billing-relevant data is no longer trusted from the client.

- **`PATCH /iap/transactions/{id}/storekit-status/`** is now a *trigger to verify* endpoint. When the SDK reports `storekit_status=2`, the backend queries Apple's API itself and persists what Apple reports.
- **`storekit_subscription_end`** in the PATCH request body is **accepted but ignored** as of this release. Existing SDKs that send the field continue to work unchanged; new SDK releases may omit it.
- **`storekit_apple_status`** is a new optional field exposed on transaction responses (e.g., [`GET /iap/transactions/{id}`](/api-reference/endpoint/get-transaction)). It carries Apple's full 5-state subscription code: `1` = Active, `2` = Expired, `3` = BillingRetry, `4` = GracePeriod, `5` = Revoked. Null when no Apple-verified state has been recorded.
- **ASSN v2 webhook events** `DID_CHANGE_RENEWAL_STATUS`, `EXPIRED`, `DID_FAIL_TO_RENEW`, `REVOKE`, and `REFUND` now mirror Apple's reported state onto the migration `Transaction` record automatically (`storekit_status`, `storekit_apple_status`, `storekit_subscription_end`) — no SDK changes required. See [Webhooks](/iap/webhooks#app-store-server-notifications) for details.
</Update>

<Update label="API" description="2026-04-26">
### GET /iap/products/ — `?demo=migration|upgrade` preview flag

A new optional `demo` query param lets debug builds surface a dashboard-configured campaign regardless of the user's real subscription state — useful for previewing your tip UI in the SDK without crafting a specific test account.

- **`demo=migration`** — surfaces the configured `MigrationCampaign` (Switch & Save) on `config.migration` (and `config.offer` mirror with `flow_type=migration`).
- **`demo=upgrade`** — surfaces the configured `UpgradeOfferConfig` (Upgrade & Save) on `config.offer` with `flow_type=upgrade`. Uses the first `upgrade_paths` entry as preview source/target. `savings_percent` is `0` for demo — accurate proration requires a real billing cycle, so previews show the layout without the dynamic numbers.
- Honored **only** when the request uses a test-mode publishable key (`zs_pk_test_*`); live keys silently ignore the flag. Impressions are not counted on demo requests.
- **iOS SDK 1.2.1+** wires this automatically via `ZSOfferManager.demoMode: ZSDemoMode = .off | .migration | .upgrade` (gate assignments behind `#if DEBUG`). The SDK forwards the chosen flow on the products fetch and disables the checkout CTA in demo mode to prevent real charges.
</Update>

<Update label="API" description="2026-04-20">
### POST /iap/storekit-transactions/ — auto-renew state sync (SDK 1.3+)

Two new optional fields on the StoreKit sync endpoint let SDK 1.3+ clients forward Apple's local auto-renew signal on every sync. The backend diffs the incoming value against the stored entitlement and emits `CANCELLED` / `REACTIVATED` events when it flips — so dashboards and retention analytics stay accurate even in deployments without App Store Server Notifications (ASSN) v2 configured.

- **`will_auto_renew`** *(boolean, optional)* — Mirror of `Product.SubscriptionInfo.RenewalInfo.willAutoRenew`. `true → false` emits `CANCELLED(store_kit)`; `false → true` emits `REACTIVATED(store_kit)`. Missing / older-SDK syncs preserve existing behavior.
- **`renewal_state`** *(string, optional, reserved)* — Mirror of `Product.SubscriptionInfo.RenewalState`. Accepted but not yet acted on. Forward-compatible hook for future SDK releases.

Both fields are idempotent per StoreKit transaction ID — repeat syncs of the same JWS never emit duplicate events.
</Update>

<Update label="API" description="2026-04-20">
### New /iap/user-offer/ endpoint (SDK 1.2+)

Unified offer + subscription-state endpoint replacing three overlapping paths.
Existing endpoints remain fully supported; old SDKs continue to work unchanged.

- **New**: [`GET /iap/user-offer/`](/api-reference/endpoint/user-offer) returns a
  canonical `UserOfferResponse` with an `action_type` discriminator
  (`no_action`, `migrate_storekit_to_web`, `upgrade_storekit_to_web`,
  `upgrade_web_to_web`), consistent `savings_percent` naming, and an
  `apple_subscription.is_active` flag that is the canonical replacement for
  client-side interpretation of raw Apple status integers.
- **New** fields on [`GET /iap/storekit-subscription-status/`](/api-reference/endpoint/get-storekit-subscription-status):
  `is_active` (normalized from the Apple status code) and `auto_renew_enabled`
  (normalized from `auto_renew_status`). The raw `status` and `auto_renew_status`
  fields remain for backward compatibility but are now diagnostic only.
- **Non-breaking**: [`GET /iap/products/`](/api-reference/endpoint/get-products)
  and [`GET /iap/upgrade-offer/`](/api-reference/endpoint/get-upgrade-offer) now
  derive their responses from the same resolver. Wire format is byte-identical.
</Update>

<Update label="API" description="2026-04-18">
### POST /iap/payment-intents — optional Apple reporting fields

Two new optional fields are now accepted by the `POST /iap/payment-intents/` endpoint. Existing clients that omit them continue to work without changes.

- **`external_purchase_token`** *(string, optional)* — The `externalPurchaseToken` received from StoreKit at the disclosure-sheet confirmation step. When provided, ZeroSettle stores the token and uses it for automatic external-purchase reporting in eligible jurisdictions (EU/EEA under the DMA alternative terms, EEA music streaming, and Japan MSCA on iOS 26.4+). No action required for apps outside those regions.
- **`ios_version`** *(string, optional)* — iOS version of the checkout client (e.g., `"26.4.1"`). Used for JP MSCA regime gating, which requires iOS 26+. Provide this field when targeting Japanese users on iOS 26+.

Both fields are persisted on the resulting `Transaction` record and surfaced in the Apple Reporting dashboard.
</Update>

<Update label="1.1.5" description="2026-04-15">
### Entitlement ownership, checkout hardening, and claim API

This release overhauls how StoreKit entitlements are attributed across accounts sharing the same Apple ID, hardens the checkout presentation pipeline, and adds an explicit API for entitlement transfers.

#### Entitlement Ownership Model

StoreKit entitlements now belong permanently to the account that was active when the purchase was made. When multiple app accounts share the same Apple ID, each account only sees its own purchases — no automatic transfers.

- **Ownership-aware sync** — `syncCurrentTransactions()` returns ownership decisions from the server; the SDK filters local StoreKit entitlements accordingly
- **`claimEntitlement(productId:userId:)`** — Explicit API to transfer a StoreKit entitlement from another account to the current one. For testing, account migration, and support tools.
- **Zero public API changes** — Ownership filtering is internal. `bootstrap()`, `restoreEntitlements()`, and `activeEntitlements` work exactly as before.

See [Entitlement Ownership](/iap/entitlement-ownership) for the full guide.

#### Checkout Hardening

- **`buttonsReady` gate** — The checkout sheet no longer presents until Apple Pay / card buttons are fully rendered. Eliminates the flash of incomplete payment UI.
- **`pool.ensureReady(for:url:)`** — Single entry point for WebView readiness, used by all checkout modifier variants. Centralizes the `isAlive` → `reset` → `loadAndWait` → `waitForButtonsReady` sequence.
- **JS handler safety** — The `default` case in the WebView message handler now requires terminal fields (`success`, `cancelled`, `error`) before marking checkout complete. Prevents unrecognized JS actions from triggering false "Payment failed" errors.
- **409 retry** — `initiateCheckout()` retries once on 409 (concurrent batch/individual PI race) with a clamped 0.1–5s delay.

#### Offer System Improvements

- **OfferTipView spinner fix** — `ctaTapped` is now reset after sheet checkout completes, preventing an infinite spinner in the accepted state.
- **ZSOfferManager hardening** — State machine documentation, logging on all silent guard returns, and `activeStoreKitEntitlements` helper to eliminate 4x duplicated filter.
- **`MigrationTipView` deprecated** — Use `OfferTipView` instead. Compiler warning guides migration.
- **`appAccountToken`** — StoreKit purchases now set `appAccountToken` so App Store Server Notifications (ASSN) webhooks can resolve the correct user identity without waiting for SDK sync.

#### Error Improvements

- Checkout failure alerts now include the product ID and actionable guidance: *"Failed to create payment for \<productId\>. Check that the product has a valid web price configured in the ZeroSettle dashboard."*
- PI creation errors are logged with the actual server error instead of being silently swallowed.

Includes patch tags 1.1.1, 1.1.2, 1.1.3, 1.1.4 with internal fixes.
</Update>

<Update label="1.1.0" description="2026-04-07">
### Unified offer system

New `OfferTipView` and `ZSOfferManager` unify migration and upgrade offers into a single component. The server determines which offer to show based on the user's subscription state — no app update needed to switch between offer types.

Note: patch tags 1.0.32, 1.0.33, and 1.0.34 shipped between 1.0.31 and 1.1.0 with internal fixes.

- **`OfferTipView`** — Drop-in replacement for `MigrationTipView` that handles migration, storekit-to-web upgrades, and web-to-web upgrades
- **`ZSOfferManager`** — Headless state machine for custom offer UI (replaces `ZSMigrationManager` for new integrations)
- **`Offer.Display`** — 8 server-configurable copy fields for every card state (offer, accepted, completed)
- **Checkout presentation modes** — `inline` (WebView within card) or `sheet` (overlay), configurable from dashboard
- **Minimize / collapse** — Close button becomes a collapse chevron when checkout is expanded, letting users back out without dismissing the entire offer
- **`config.offer`** — New unified field in products response alongside existing `config.migration` for backward compatibility

`MigrationTipView` continues to work unchanged. It auto-adopts server-provided copy from the unified offer system when available.
</Update>

<Update label="1.0.26" description="2026-03-22">
### Batch checkout & trial fields

New batch endpoint and trial metadata fields for the checkout API:

- **`POST /v1/iap/payment-intents/batch/`** — Create payment intents for up to 25 products in a single request. Reduces checkout latency by sharing Stripe customer/account resolution across products. Products that fail validation return per-product errors without failing the batch.
- **`trial_type`** field on payment intent responses — indicates whether a trial is a standard `free_trial` or a Switch & Save `migration` trial.
- **`trial_end`** and **`pending_amount`** fields on payment intent responses — Unix timestamp of trial expiry and the deferred charge amount.

These are additive, non-breaking changes. Existing integrations are unaffected.
</Update>
