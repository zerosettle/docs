ZeroSettle establishes user identity **once per session** with `identify(...)`, which you call after `configure()` and before any purchase, product-fetch, or entitlement call. Identity is then implicit — you do not pass a `userId` to individual methods.

<Note>
  **Identify-first is required.** On iOS, Android, and Flutter, calling a user-scoped method (`purchase`, `restoreEntitlements`, etc.) before `identify()` throws a "user not identified" error. The React Native SDK (currently one version behind) still uses the older `bootstrap(userId)` model — see the React Native tabs below.
</Note>

## The `Identity` Type

`identify()` takes an `Identity` value. If your app has accounts, the recommended flow is `identify(.anonymous)` at launch and `identify(.user(id:))` when the person signs in. From the next SDK release, ZeroSettle folds the anonymous id into the account for you, see [Option 3](#option-3-anonymous-users). Before that release, pick one mode per person and do not switch between them.

| Mode | When to use |
|------|-------------|
| `Identity.user(id:)` | You have your own auth system. Pass a stable user ID. |
| `Identity.anonymous` | No auth system. The SDK generates and persists a stable session UUID. |
| `Identity.deferred` | Auth comes on a later screen. A placeholder, not an identity — see [Deferring identification](#deferring-identification). |

<Note>
  On Swift these are enum cases — write `.anonymous` and `.deferred`, with no parentheses. On Kotlin, `Identity` is a sealed class: write `Identity.Anonymous` and `Identity.Deferred` (objects, no parentheses) and `Identity.User(id = ...)`. Flutter's `Identity` is a class with factory constructors, so Dart spells the same two `Identity.anonymous()` and `Identity.deferred()`.
</Note>

### Deferring identification

Many apps start the SDK before they know who the user is — `configure()` runs at launch, but auth resolves a screen or two later. `Identity.deferred` is how you say so.

<Warning>
  **`.deferred` is not an identity, and you cannot purchase under it.** It sets a flag that suppresses the 10-second "no user identified" warning and does nothing else: it creates no user on our side, returns `null` instead of a catalog, and does **not** satisfy the identify-first requirement. `purchase()`, `restoreEntitlements()` and every other user-scoped call keep throwing "user not identified" until you call `identify()` again with `Identity.user(id:)` or `Identity.anonymous`.

  Because no purchase can happen while you are deferred, there is never an earlier transaction to re-attribute when the real identity arrives — and correspondingly, `.deferred` never appears in a [webhook event](/iap/event-webhooks). Every event carries the identity the purchase was actually made under.
</Warning>

```swift Swift
// At launch — you don't know who this is yet.
ZeroSettle.shared.configure(.init(publishableKey: "zs_pk_live_..."))
try await ZeroSettle.shared.identify(.deferred)   // returns nil, no catalog yet

// ...later, once sign-in completes. This is the call that creates the
// identity, fetches the catalog and restores entitlements.
let catalog = try await ZeroSettle.shared.identify(.user(id: user.id))

// Only now can this succeed.
let transaction = try await ZeroSettle.shared.purchase(productId: "premium_monthly")
```

Gate your paywall on the second `identify()` having completed. If a user can reach a buy button before you know who they are, you have two choices — block the purchase until they sign in, or call `identify(.anonymous)` and accept that the purchase is tied to that install until your server moves it to an account (see [Guest to Account](/iap/guest-to-account)).

<Note>
  Unrelated: elsewhere in these docs "deferred mode" refers to a checkout warmup optimisation in the SDK's networking layer. It has nothing to do with `Identity.deferred`.
</Note>

## Reading the current id

The SDK exposes the id it is acting as, and an id for analytics that is available before sign-in.

`analyticsUserId` is new in the next SDK release on every platform. On iOS, `currentUserId` also becomes public in that release. Android (`ZeroSettle.currentUserId`) and Flutter (`getCurrentUserId()`) already have it.

| Property | What it returns |
|---|---|
| `currentUserId` | The id the SDK is acting as: your id after `identify(.user)`, the generated id after `identify(.anonymous)`. In the next SDK release a new install's generated id starts with `zs_anon_`. `nil` before any `identify()` and after `logout()` |
| `analyticsUserId` | Set before sign-in too. The current id when there is one, otherwise a per-device UUID that is generated and stored on first use. It is the same id `identify(.anonymous)` adopts later (a `zs_anon_` id on new installs), so paywall views recorded before identify join the purchase made after it |

<CodeGroup>

```swift Swift
let signedInAs: String? = ZeroSettle.shared.currentUserId   // read-only
let eventsId: String = ZeroSettle.shared.analyticsUserId    // never empty
```

```kotlin Kotlin
val signedInAs: String? = ZeroSettle.currentUserId.value    // StateFlow, read-only
val eventsId: String? = ZeroSettle.analyticsUserId()        // suspend, null only before configure()
```

```dart Flutter
final String? signedInAs = await ZeroSettle.instance.getCurrentUserId();
final String eventsId = await ZeroSettle.instance.analyticsUserId();
```

</CodeGroup>

<Note>
  On iOS, `currentUserId` is not observable by SwiftUI, so a view will not refresh when it changes. Track your own signed-in state for UI, and use these properties to read which id the SDK is using, for example to hand a guest id to your server at sign-up. See [Guest to Account](/iap/guest-to-account).
</Note>

<Warning>
  **Do not switch signed-in users without `logout()`.** Calling `identify(.user(id: B))` while user A is signed in makes the SDK act as B, but purchases made as A stay with A, and nothing tells ZeroSettle that A and B are the same person. The SDK logs a warning when this happens. Call `logout()` first when a different person signs in. If A and B really are the same person (a guest who just signed up), have your server [reconcile](/iap/guest-to-account) the two ids instead.
</Warning>

## Option 1: RevenueCat Users

If you use RevenueCat for subscription management, pass the same user ID to `identify()`:

<CodeGroup>

```swift Swift
import SwiftUI
import ZeroSettleKit
import RevenueCat

// Configure - disable StoreKit sync since RevenueCat handles it
ZeroSettle.shared.configure(.init(
    publishableKey: "zs_pk_live_...",
    syncStoreKitTransactions: false
))

// Identify once, using your RC user ID
let catalog = try await ZeroSettle.shared.identify(
    .user(id: Purchases.shared.appUserID)
)

// Purchase - identity is implicit, no userId needed
let transaction = try await ZeroSettle.shared.purchase(productId: "premium_monthly")
```

```kotlin Kotlin
import com.zerosettle.sdk.ZeroSettle
import com.zerosettle.sdk.ZeroSettleConfig
import com.zerosettle.sdk.Identity

// Configure - disable Play Billing purchase sync since RevenueCat handles it
ZeroSettle.configure(context, ZeroSettleConfig(
    publishableKey = "zs_pk_live_...",
    syncPlayPurchases = false,
))

// Identify once, using your RC user ID
ZeroSettle.identify(Identity.User(id = Purchases.sharedInstance.appUserID))

// Purchase - identity is implicit, no userId needed
val transaction = ZeroSettle.purchase(
    activity = this, productId = "premium_monthly",
).getOrThrow()
```

```tsx React Native
import { ZeroSettleKit } from 'react-native-zerosettle';

// Configure with StoreKit sync disabled
ZeroSettleKit.configure({
  publishableKey: 'zs_pk_live_...',
  syncStoreKitTransactions: false,
});

// React Native (1.1.0) uses the bootstrap(userId) model
await ZeroSettleKit.bootstrap(Purchases.getAppUserID());

// Purchase using RC user ID
const transaction = await ZeroSettleKit.purchase(
  'premium_monthly',
  Purchases.getAppUserID(),
);
```

```dart Flutter
import 'package:zerosettle/zerosettle.dart';

// Configure with StoreKit sync disabled
await ZeroSettle.instance.configure(
  publishableKey: 'zs_pk_live_...',
  syncStoreKitTransactions: false,
);

// Identify once, using your RC user ID
await ZeroSettle.instance.identify(
  Identity.user(id: Purchases.appUserID),
);

// Purchase - identity is implicit, no userId needed
final transaction = await ZeroSettle.instance.purchase(
  productId: 'premium_monthly',
);
```

</CodeGroup>

**How it works**: ZeroSettle processes the web payment and pushes it to RevenueCat via webhook. RevenueCat manages entitlements—you query RC as usual.

**Restoration**: RevenueCat handles it. Call `Purchases.shared.restorePurchases()`.

<Note>
  `syncStoreKitTransactions: false` (iOS / Flutter) and `syncPlayPurchases = false` (Android) keep native store purchases out of ZeroSettle, leaving RevenueCat as the only place they are reported. Leave the listener **on** if you want ZeroSettle to track them too — see [RevenueCat Integration](/iap/revenuecat-integration) for the trade-off, and [Analytics-Only Integration](/iap/analytics-only) for that setup on its own.
</Note>

## Option 2: Custom Auth (Recommended)

If you have your own authentication system:

<CodeGroup>

```swift Swift
import SwiftUI
import ZeroSettleKit

// Configure
ZeroSettle.shared.configure(.init(publishableKey: "zs_pk_live_..."))

// Identify once, after login
let catalog = try await ZeroSettle.shared.identify(
    .user(id: Auth.currentUser.id)
)

// Purchase - identity is implicit
let transaction = try await ZeroSettle.shared.purchase(productId: "premium_monthly")

// Later: restore entitlements (no userId — identity is implicit)
let entitlements = try await ZeroSettle.shared.restoreEntitlements()
```

```kotlin Kotlin
import com.zerosettle.sdk.ZeroSettle
import com.zerosettle.sdk.ZeroSettleConfig
import com.zerosettle.sdk.Identity

// Configure
ZeroSettle.configure(context, ZeroSettleConfig(
    publishableKey = "zs_pk_live_..."
))

// Identify once, after login
ZeroSettle.identify(Identity.User(id = auth.currentUser.id))

// Purchase - identity is implicit (purchase() returns Result<CheckoutTransaction>)
val transaction = ZeroSettle.purchase(activity = this, productId = "premium_monthly").getOrThrow()

// Later: restore entitlements (no userId — identity is implicit)
val entitlements = ZeroSettle.restoreEntitlements().getOrThrow()
```

```tsx React Native
import { ZeroSettleKit } from 'react-native-zerosettle';

ZeroSettleKit.configure({ publishableKey: 'zs_pk_live_...' });

// React Native (1.1.0): bootstrap with your user ID
await ZeroSettleKit.bootstrap(auth.currentUser.id);

const transaction = await ZeroSettleKit.purchase(
  'premium_monthly',
  auth.currentUser.id,
);

const entitlements = await ZeroSettleKit.restoreEntitlements(auth.currentUser.id);
```

```dart Flutter
import 'package:zerosettle/zerosettle.dart';

await ZeroSettle.instance.configure(publishableKey: 'zs_pk_live_...');

// Identify once, after login
await ZeroSettle.instance.identify(
  Identity.user(id: auth.currentUser.id),
);

// Purchase - identity is implicit
final transaction = await ZeroSettle.instance.purchase(
  productId: 'premium_monthly',
);

// Later: restore entitlements (no userId — identity is implicit)
final entitlements = await ZeroSettle.instance.restoreEntitlements();
```

</CodeGroup>

**How it works**: ZeroSettle links purchases to the identity from your most recent `identify()` call and tracks entitlements. `restoreEntitlements()` fetches all active entitlements from both web checkout and native store sources.

**Restoration**: Call `identify()` after login (or on app launch), then `restoreEntitlements()`. Works across devices.

<Info>
  StoreKit purchases are tied to the account that was logged in when the purchase was made. If multiple accounts share the same Apple ID, each only sees its own purchases. See [Entitlement Ownership](/iap/entitlement-ownership).
</Info>

## Option 3: Anonymous Users

No user system yet? Use `Identity.anonymous`. The SDK generates and persists a stable per-install UUID, so entitlements remain restorable for the lifetime of the install — no email lookup required.

<CodeGroup>

```swift Swift
import SwiftUI
import ZeroSettleKit

// Configure
ZeroSettle.shared.configure(.init(publishableKey: "zs_pk_live_..."))

// Identify anonymously — the SDK persists a stable session UUID
let catalog = try await ZeroSettle.shared.identify(.anonymous)

// Purchase — identity is implicit
let transaction = try await ZeroSettle.shared.purchase(productId: "premium_lifetime")
```

```kotlin Kotlin
import com.zerosettle.sdk.ZeroSettle
import com.zerosettle.sdk.ZeroSettleConfig
import com.zerosettle.sdk.Identity

// Configure
ZeroSettle.configure(context, ZeroSettleConfig(publishableKey = "zs_pk_live_..."))

// Identify anonymously — the SDK persists a stable per-install UUID
ZeroSettle.identify(Identity.Anonymous)

// Purchase — identity is implicit
val transaction = ZeroSettle.purchase(
    activity = this, productId = "premium_lifetime",
).getOrThrow()
```

```tsx React Native
// React Native (1.1.0) does not yet expose the Identity model.
// Pass an empty string to bootstrap for an anonymous session.
import { ZeroSettleKit } from 'react-native-zerosettle';

ZeroSettleKit.configure({ publishableKey: 'zs_pk_live_...' });

await ZeroSettleKit.bootstrap('');

const transaction = await ZeroSettleKit.purchase('premium_lifetime', '');
```

```dart Flutter
import 'package:zerosettle/zerosettle.dart';

await ZeroSettle.instance.configure(publishableKey: 'zs_pk_live_...');

// Identify anonymously — the SDK persists a stable session UUID
await ZeroSettle.instance.identify(Identity.anonymous());

// Purchase — identity is implicit
final transaction = await ZeroSettle.instance.purchase(
  productId: 'premium_lifetime',
);
```

</CodeGroup>

**How it works**: `Identity.anonymous` persists a stable id in on-device storage. The same identity is reused across app launches until you call `logout()` or the user clears app data. From the next SDK release, a new install's anonymous id looks like `zs_anon_<uuid>`. An install that already has an anonymous UUID keeps it, and that id does not get the automatic merge below.

**Restoration**: `restoreEntitlements()` works for anonymous users. Entitlements are tied to the persisted id.

### Anonymous first, then sign in

If your app has accounts, call `identify(.anonymous)` at launch, then `identify(.user(id:))` when the person signs in. The person counts as an active user from first launch, before sign-in, and counts once after.

<CodeGroup>

```swift Swift
// At launch
try await ZeroSettle.shared.identify(.anonymous)

// When the person signs in
try await ZeroSettle.shared.identify(.user(id: account.id))
```

```kotlin Kotlin
// At launch
ZeroSettle.identify(Identity.Anonymous)

// When the person signs in
ZeroSettle.identify(Identity.User(id = account.id))
```

```dart Flutter
// At launch
await ZeroSettle.instance.identify(Identity.anonymous());

// When the person signs in
await ZeroSettle.instance.identify(Identity.user(id: account.id));
```

</CodeGroup>

At sign-in the SDK asks ZeroSettle to fold the anonymous id into the account:

- **The account has no history yet** (no purchases, entitlements, Stripe customer or funnel events). Everything moves: purchases, entitlements, events and experiment assignments. The person counts once in active users, and an [`identity.reconciled`](/iap/event-webhooks#identity-reconciled) webhook fires with `actor` of `identity_link` and `from_user_id` set to the `zs_anon_` id.
- **The account already has history.** Nothing moves. The app switches to the account. The guest's purchases can move later through Restore Purchases or the server-side reconcile in [Guest to Account](/iap/guest-to-account).

Retries are safe. If the call fails, the SDK retries on the next launch or sign-in.

<Warning>
  **Make user ids hard to guess.** The merge is authorized by your publishable key, so use a random UUID or your auth provider's opaque id for `Identity.user(id:)`. Do not use an email or a sequential number.

  The `zs_anon_` prefix is reserved. `identify(.user(id:))` with an id that starts with it fails with an invalid user id error, and the server refuses it as a merge target (`into_anonymous` on reconcile, `invalid_user_id` with status 400 on `identity-link`).
</Warning>

<Warning>
  **An anonymous id is install-scoped.** The id lives on the device, so a reinstall or an app-data clear loses it. A reinstall gets a new anonymous id, and it folds into the account when the person signs in again.

  Before the next SDK release, calling `identify(.user(id:))` starts a new identity and the guest's purchase history stays behind on the old one. Your server can move it, see [Guest to Account](/iap/guest-to-account). You can also mint a stable identifier you own on first launch and pass it to `Identity.user(id:)` from day one, see [Picking an identity on iOS](#picking-an-identity-on-ios).
</Warning>

## Picking an identity on iOS

The identity you pass to `Identity.user(id:)` should be non-guessable, stable for the life of the account, and never reused by a different person. Three options, best first:

**Sign in with Apple.** If your app has a Sign in with Apple button, `ASAuthorizationAppleIDCredential.user` is the strongest identifier available on the platform. It is opaque, scoped to your developer team, stable forever for that Apple ID, identical on every device the person signs into, and it survives a reinstall. It is also scoped to the same Apple ID that owns their StoreKit purchases, which makes it the right identity for a *payer* rather than merely a convenient one.

```swift
SignInWithAppleButton(.signIn) { request in
    request.requestedScopes = [.fullName, .email]
} onCompletion: { result in
    guard case .success(let auth) = result,
          let credential = auth.credential as? ASAuthorizationAppleIDCredential
    else { return }

    // Persist credential.user in the Keychain — it is not re-issued on
    // subsequent sign-ins, and getCredentialState(forUserID:) needs it.
    Keychain.store(appleUserID: credential.user)

    Task { try? await ZeroSettle.shared.identify(.user(id: credential.user)) }
}
```

**Your backend's user ID.** A UUID your server minted at signup. Equally good, if you have a server.

**An ID you mint on device.** No accounts and no backend, but you expect them later: generate a `UUID()` on first launch and store it in the Keychain (which survives reinstall, unlike `UserDefaults`). Pass it to `Identity.user(id:)` from the very first launch. This costs nothing now and keeps the guest's id under your control.

<Note>
  The ID does not need to be a UUID. The SDK derives Apple's `appAccountToken` as a UUIDv5 over whatever string you pass, so Firebase UIDs, Auth0 `sub` values, and Apple's opaque user identifier all work as-is. Don't reshape your IDs to satisfy the SDK.
</Note>

<Warning>
  Never use `identifierForVendor`, an advertising identifier, an email address, or any constant. A constant is the worst of these — it makes every install look like one customer and can hand out entitlements nobody paid for.
</Warning>

## Checking Entitlements

After restoring entitlements, check if a user has access:

<CodeGroup>

```swift Swift
// Identity is implicit — call identify() once first, no userId here
let entitlements = try await ZeroSettle.shared.restoreEntitlements()

// Check for a specific product
let hasPremium = entitlements.contains {
    $0.productId == "premium_monthly" && $0.isActive
}

// Or check if any entitlement is active
let hasAnyAccess = entitlements.contains { $0.isActive }
```

```kotlin Kotlin
// Identity is implicit — call identify() once first, no userId here
val entitlements = ZeroSettle.restoreEntitlements().getOrThrow()

// Check for a specific product
val hasPremium = entitlements.any {
    it.productId == "premium_monthly" && it.isActive
}

// Or check if any entitlement is active
val hasAnyAccess = entitlements.any { it.isActive }
```

```tsx React Native
// React Native (1.1.0) still takes the userId argument
const entitlements = await ZeroSettleKit.restoreEntitlements(currentUser.id);

const hasPremium = entitlements.some(
  e => e.productId === 'premium_monthly' && e.isActive
);

const hasAnyAccess = entitlements.some(e => e.isActive);
```

```dart Flutter
// Identity is implicit — call identify() once first, no userId here
final entitlements = await ZeroSettle.instance.restoreEntitlements();

final hasPremium = entitlements.any(
  (e) => e.productId == 'premium_monthly' && e.isActive,
);

final hasAnyAccess = entitlements.any((e) => e.isActive);
```

</CodeGroup>

Each `Entitlement` includes:

| Property | Type | Description |
|----------|------|-------------|
| `id` | `String` | Unique entitlement identifier |
| `productId` | `String` | The product ID this entitlement grants |
| `source` | `Entitlement.Source` | `.webCheckout` or `.storeKit`. Android's equivalent adds `.playStore` |
| `isActive` | `Bool` | Whether currently valid |
| `status` | `Entitlement.Status` | `.active`, `.paused`, `.expired`, `.revoked`, `.cancelled`, `.gracePeriod`, `.pastDue`, or `.unknown(String)` |
| `expiresAt` | `Date?` | Expiration date for subscriptions |
| `purchasedAt` | `Date` | When this transaction was purchased |
| `originalPurchaseDate` | `Date?` | When the subscription first started, across renewals |

### Renewal and cancellation

| Property | Type | Description |
|----------|------|-------------|
| `willRenew` | `Bool` | Whether the subscription is set to auto-renew |
| `isCancelled` | `Bool` | Cancelled but still inside the paid period — access continues until `expiresAt` |
| `cancelledAt` | `Date?` | When the user cancelled |

### Trials

| Property | Type | Description |
|----------|------|-------------|
| `isTrial` | `Bool` | Whether this entitlement is currently in its free trial |
| `trialEndsAt` | `Date?` | When the trial converts to paid |
| `trialDaysRemaining` | `Int?` | Whole days left in the trial, or `nil` outside one |

### Pause

| Property | Type | Description |
|----------|------|-------------|
| `isPaused` | `Bool` | Whether the subscription is paused |
| `pausedAt` | `Date?` | When the pause began |
| `pauseResumesAt` | `Date?` | When billing resumes |

### StoreKit linkage

| Property | Type | Description |
|----------|------|-------------|
| `storekitOriginalTransactionId` | `String?` | Apple's `originalTransactionId` for entitlements that came from StoreKit |

<Tip>
  `status`, `isCancelled`, and the trial fields are what you want for paywall and settings copy — "trial ends in 3 days", "cancels on the 14th", "payment failed". `isActive` alone can't tell those apart.
</Tip>

## Entitlement Sources

Entitlements can come from three sources:

- **`.webCheckout`**: Purchases made through ZeroSettle's Stripe checkout
- **`.storeKit`**: Purchases made through Apple's native StoreKit (if `syncStoreKitTransactions: true`)
- **`.playStore`**: Purchases made through Google Play Billing (if `syncPlayPurchases = true`)

The SDK merges entitlements from all sources when you call `restoreEntitlements()`.

## Best Practices

<AccordionGroup>
  <Accordion title="Call identify() once per session">
    Call `identify()` after `configure()` and after login — before any product-fetch, purchase, or entitlement call. You do not pass a `userId` to individual methods; identity is implicit from the most recent `identify()`.
  </Accordion>
  <Accordion title="Use a stable identity ID">
    Pass a stable identifier to `Identity.user(id:)` that doesn't change. UUIDs work well. Avoid using email addresses directly as they can change.
  </Accordion>
  <Accordion title="Log out before another person signs in">
    Call `logout()` when the signed-in person changes. Switching `identify(.user(id:))` from one user to another without it leaves the first user's pending work attached to the first id, and the SDK logs a warning.
  </Accordion>
  <Accordion title="Call restoreEntitlements on app launch">
    After `identify()`, call `restoreEntitlements()` so entitlements are synced even if the app was reinstalled, or a purchase was made on another device.
  </Accordion>
  <Accordion title="Handle the checkout callback">
    Implement the universal link handler to capture successful purchases. See the [Quickstart](/iap/quickstart) for setup.
  </Accordion>
</AccordionGroup>

## Identity ID Guidelines

| Do | Don't |
|----|-------|
| Use your backend's user ID for `Identity.user(id:)` | Use device identifiers (they change) |
| Use a UUID you generate | Use email (users change emails) |
| Keep it consistent across platforms | Use different IDs per platform |
| Use `Identity.anonymous` at launch and `Identity.user(id:)` at sign-in (next SDK release) | Pass an email or a sequential number as a user id |
