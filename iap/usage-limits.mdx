Use this to gate parts of your app by plan, and to meter AI features with credits. You set the rules once in the dashboard. Your app reads what the person has. Your server spends credits before each AI request.

## The model

| Concept | What it is |
|---|---|
| **Plan** | A named set of products, for example Pro is Pro Monthly, Pro Yearly and Lifetime. Plans are ranked. Everyone is on Free until they buy. A person has exactly one plan: the highest-ranked plan among the products they hold. |
| **Add-on** | A plan of kind `add_on`. It stacks on top of the person's plan instead of competing for rank. A person has any number of add-ons. |
| **Feature** | Something your app checks by key, for example `custom_styles`. It is either on or off, or it has a value picked from an ordered list you type, lowest to highest (`1080p`, `4K`, `8K`). Each plan and add-on sets a value for every feature. A person gets the best value across their plan and add-ons. |
| **Currency** | A counter you name, for example Credits. An app can have several. |
| **Action** | What spends a currency, with a key your server sends (`image_generation`). Its cost is a fixed number or by usage. A key you haven't listed costs 1. |
| **Source** | Where a currency comes from: a free allowance, a plan's allowance, or a purchased pack. |
| **Balance** | What one person has left in one currency. |

A person's balance adds up three parts, spent in this order: this period's allowance, then rolled-over units, then purchased units. Purchased units from a pack do not expire.

### Pack credits and disputes

A pack credits its units when the payment succeeds. A Google Play pack bought with quantity N credits N packs, and a refund of part of the quantity removes that many packs. An Apple purchase credits one pack even if the quantity is higher.

- A refund takes back the units that are still unspent. Spent units stay spent.
- A dispute (a chargeback) takes back all unspent units, as a full refund does. A dispute that is only an inquiry changes nothing, and neither does its close.
- A won dispute returns the units. An earlier partial refund stays taken.
- A balance never goes below zero.

While a chargeback is open, the buyer cannot spend the pack's units. Nothing is taken for an inquiry, which Stripe marks with a warning status, until it escalates to a chargeback.

## Set it up in the dashboard

<Steps>
  <Step title="Plans">
    Open the plans page in the catalog. ZeroSettle proposes plans from your App Store subscription groups and Play subscriptions. Rename them, move products between them, and add add-ons.
  </Step>
  <Step title="Features">
    Add the features your app checks. Pick on or off, or a value list. Set each feature's value for every plan and add-on. A feature's key can be edited until your app first checks it, then it is fixed.
  </Step>
  <Step title="Currencies">
    Add a currency, list its actions, and add its sources. Set a cost per unit (what one unit costs you in dollars). Once any action is by usage, the dashboard requires it, because ZeroSettle uses it to turn `usage` or `cost` into units. Choose what happens when someone runs out: automatic (the default, which picks an upgrade offer or credit packs), an upgrade offer, credit packs, or nothing and your app handles it. Choose what your server answers if ZeroSettle can't be reached: allow or stop.
  </Step>
</Steps>

## Check access in your app

The app reads the plan, features and balances with the publishable key. Call `identify` first: access loads for the signed-in person, and until it has, every read answers from the `offlineFeatureDefaults` you set in code. After that the SDK refreshes on return to the foreground and after a purchase or restore, and publishes an update when something changes. On iOS the foreground refresh starts once the app first reads access and runs at most once a minute. On Android the SDK also refreshes every 5 minutes while the app is in the foreground. The app never spends credits; balances are for display.

<CodeGroup>
```swift Swift
// After ZeroSettle.shared.identify(...) has run for the signed-in user
if ZeroSettle.hasAccess("custom_styles") {
    // on or off feature
}

let quality = ZeroSettle.value("export_quality")   // "4K", or nil
let credits = ZeroSettle.balance("credits")        // remaining, limit, resetsAt
let plan = ZeroSettle.plan                         // key and name

// Observe changes
for await access in ZeroSettle.shared.accessUpdates {
    // update your UI
}
```

```kotlin Kotlin
// After ZeroSettle.identify(...) has run for the signed-in user
if (ZeroSettle.hasAccess("custom_styles")) {
    // on or off feature
}

val quality = ZeroSettle.value("export_quality")   // "4K", or null
val credits = ZeroSettle.balance("credits")        // remaining, limit, resetsAt

// Observe changes with StateFlows: access, plan, features, balances
val plan by ZeroSettle.plan.collectAsState()
val balances by ZeroSettle.balances.collectAsState()
```
</CodeGroup>

- `hasAccess` is true for an on feature, and for a value feature that has a value.
- `value` returns the value of a value feature, and `nil` or `null` for an on-or-off feature or an unknown key.
- Display a balance as "318 of 500 left" from `remaining` and `limit`.

### First launch with no connection

The SDK keeps the last answer on the device. Until access has loaded for the signed-in person, from the cache or the network (a first launch while offline, for example), each feature falls back to the offline default you set. A feature with no default is off. Set defaults in code, in the configuration. The dashboard has no offline setting.

<CodeGroup>
```swift Swift
ZeroSettle.shared.configure(.init(
    publishableKey: "zs_pk_live_...",
    offlineFeatureDefaults: ["custom_styles": .bool(false), "export_quality": .text("1080p")]
))
```

```kotlin Kotlin
ZeroSettle.configure(
    context,
    ZeroSettleConfig(
        publishableKey = "zs_pk_live_...",
        offlineFeatureDefaults = mapOf(
            "custom_styles" to FeatureValue.Bool(false),
            "export_quality" to FeatureValue.Text("1080p"),
        ),
    ),
)
```
</CodeGroup>

Checking a key with `hasAccess` or `value` tells ZeroSettle the app uses it. When that feature exists in the dashboard for the same environment, its key is then locked so it can't be renamed by mistake. The SDK reports each key once per launch, so if you create a feature after the app already checked its key, relaunch the app.

The raw data behind these reads is on the [app read endpoint](/api-reference/endpoint/get-entitlements): `plan`, `add_ons`, `features` and `balances`. Feature keys come back exactly as you named them, for example `custom_styles`.

## Spend credits from your server

Spending runs on your server with a **secret key** (`zs_sk_test_...` or `zs_sk_live_...`). Never ship a secret key in an app. The key picks sandbox or live, and the two never mix. The `user_id` is your own stable id for the person, the same one the app passes when it identifies the user. An unknown id is created as a new person on Free.

<CodeGroup>
```js Node
const resp = await fetch("https://api.zerosettle.io/v1/usage/", {
  method: "POST",
  headers: {
    "X-ZeroSettle-Key": process.env.ZEROSETTLE_SECRET_KEY,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    user_id: "user_8f21",
    action: "image_generation",
    idempotency_key: crypto.randomUUID(),
  }),
  signal: AbortSignal.timeout(2000),
});
const r = await resp.json();
if (r.status !== "allowed") {
  return res.status(402).json({ upgrade: r.upgrade_available, packs: r.packs });
}
// run the model
```

```python Python
import os, uuid, requests

resp = requests.post(
    "https://api.zerosettle.io/v1/usage/",
    headers={"X-ZeroSettle-Key": os.environ["ZEROSETTLE_SECRET_KEY"]},
    json={
        "user_id": "user_8f21",
        "action": "image_generation",
        "idempotency_key": str(uuid.uuid4()),
    },
    timeout=2,
)
resp.raise_for_status()
r = resp.json()
if r["status"] != "allowed":
    ...  # stop here
```

```bash curl
curl -X POST https://api.zerosettle.io/v1/usage/ \
  -H "X-ZeroSettle-Key: $ZEROSETTLE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user_8f21", "action": "image_generation", "idempotency_key": "req_7c1e"}'
```
</CodeGroup>

A successful answer looks like this. A denied request (`limit_reached`, `not_in_plan`) is also a `200`, spends nothing, and may carry `upgrade_available` or `packs`.

```json
{
  "status": "allowed",
  "usage_id": "use_01JAX9W3F8T2",
  "currency": {"key": "credits", "name": "Credit", "plural": "Credits", "glyph": "sparkles", "offline": "allow"},
  "spent": 3,
  "held": false,
  "remaining": 497,
  "limit": 500,
  "resets_at": "2026-11-03T00:00:00Z",
  "plan": {"key": "pro", "name": "Pro", "kind": "tier"},
  "add_ons": [],
  "upgrade_available": null,
  "packs": null,
  "test_purchase": false
}
```

The full request and response are in [Spend Usage](/api-reference/endpoint/spend-usage). To read a balance without spending, use [Read Balances](/api-reference/endpoint/get-usage).

### Idempotency and undo

Send an `idempotency_key` so a retry does not spend again. A retry with the same key within 24 hours returns the first answer and spends nothing more; after 24 hours it is a new request. The same key within 24 hours with a different body is `409 idempotency_key_reused`. Generate a new key for each request and reuse it on a retry.

If you send the same key after you undid its request, the answer is `409 request_undone`. Send a new key to spend again.

The `action` key is trimmed and lowercased before it is matched, so `Image_Generation ` and `image_generation` are one action. A key you have not listed costs 1.

If the work fails after you spent, give the units back with [Undo a Request](/api-reference/endpoint/undo-usage). It works within 24 hours of the request; after that the request is gone and undo answers `404 not_found`.

**What ZeroSettle keeps.** Each request can be finished, undone or retried for 24 hours. After that it is no longer available, and its usage stays only in the daily totals per person.

<CodeGroup>
```js Node
await fetch(`https://api.zerosettle.io/v1/usage/${r.usage_id}/undo/`, {
  method: "POST",
  headers: { "X-ZeroSettle-Key": process.env.ZEROSETTLE_SECRET_KEY },
  signal: AbortSignal.timeout(2000),
});
```

```python Python
requests.post(
    f"https://api.zerosettle.io/v1/usage/{r['usage_id']}/undo/",
    headers={"X-ZeroSettle-Key": os.environ["ZEROSETTLE_SECRET_KEY"]},
    timeout=2,
)
```

```bash curl
curl -X POST https://api.zerosettle.io/v1/usage/use_01JAX9W3F8T2/undo/ \
  -H "X-ZeroSettle-Key: $ZEROSETTLE_SECRET_KEY"
```
</CodeGroup>

## By-usage actions

A by-usage action, such as a long chat, only knows its size after the AI call returns. Every by-usage field is optional, so you pick either pattern. Fixed-cost actions never need `finish`.

**Report once, after the call.** Send `use` with `amount`, or with `usage` and `model`, once the call returns. It is one request and is charged for what you report, provided ZeroSettle can price it (see below). The status arrives after the units are spent. If less is left than you report, it takes what is left, answers `allowed` with `spent` below what you reported, and records the rest as uncharged. It answers `limit_reached` only when nothing is left. The balance never goes below zero.

**Hold, then finish.** This is the recommended pattern for by-usage actions.

1. Before the AI call, send `use` with an `estimate`. ZeroSettle holds that many units and answers. A hold comes off the balance at once, so a second request while it is open sees the lower balance.
2. After the call, send `finish` with the real usage. ZeroSettle settles the difference. Settling can take a balance to zero, never below; any excess is recorded as uncharged usage and is not carried as debt.
3. If no finish arrives within 15 minutes, the hold settles at its estimate. A finish within 24 hours of the hold still updates cost to serve but not the charge; after 24 hours finish answers `404 not_found`.

<CodeGroup>
```js Node
const base = "https://api.zerosettle.io/v1/usage/";
const headers = {
  "X-ZeroSettle-Key": process.env.ZEROSETTLE_SECRET_KEY,
  "Content-Type": "application/json",
};

const hold = await (await fetch(base, {
  method: "POST",
  headers,
  body: JSON.stringify({ user_id: userId, action: "chat", estimate: 40 }),
  signal: AbortSignal.timeout(2000),
})).json();
if (hold.status !== "allowed") return denied(hold);

const completion = await openai.chat.completions.create({ model: "gpt-4o-mini", messages });

await fetch(`${base}${hold.usage_id}/finish/`, {
  method: "POST",
  headers,
  body: JSON.stringify({ usage: completion.usage, model: completion.model }),
  signal: AbortSignal.timeout(2000),
});
```

```python Python
base = "https://api.zerosettle.io/v1/usage/"
headers = {"X-ZeroSettle-Key": os.environ["ZEROSETTLE_SECRET_KEY"]}

hold = requests.post(base, headers=headers, timeout=2, json={
    "user_id": user_id, "action": "chat", "estimate": 40,
}).json()
if hold["status"] != "allowed":
    ...  # stop here

completion = client.chat.completions.create(model="gpt-4o-mini", messages=messages)

requests.post(f"{base}{hold['usage_id']}/finish/", headers=headers, timeout=2, json={
    "usage": completion.usage.model_dump(), "model": completion.model,
})
```

```bash curl
curl -X POST https://api.zerosettle.io/v1/usage/use_01JAX9W3F8T2/finish/ \
  -H "X-ZeroSettle-Key: $ZEROSETTLE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"amount": 812}'
```
</CodeGroup>

See [Finish a Hold](/api-reference/endpoint/finish-usage) for the response.

When the model is not in ZeroSettle's price catalog and you sent token `usage` with no `cost`, the spend and finish answers carry `"warning": "unknown_model"`. The request still succeeds. Send `cost` or `amount` for that model so the charge matches the call.

### When usage can't be priced

Turning `usage` or `cost` into units needs the currency's cost per unit, plus a cost: a `cost` you send, a `cost` inside `usage`, or a model ZeroSettle can price, in that order. When the usage can't be priced, such as an unknown model with no cost:

- `use` holds the `estimate`, else the action's 7-day average, else 1, and answers `held: true`. You are charged that, not the reported usage.
- `finish` never errors for this. The hold settles at its amount and the usage is recorded.

When the model may not price, send `amount` (in the action's unit) or `cost`, so the charge matches the call.

## What to send for each provider

Send the provider's raw `usage` object and the model id. ZeroSettle maps the fields itself, so you don't convert the fields. It also records what each request cost you, so the dashboard can show margin. The cost comes from a `cost` you send, then a `cost` inside `usage`, then the catalog price for `usage` with the model. When none of them applies, the dashboard says "Not measured" and a by-usage charge falls back as described above. The table lists the providers whose model ids price today.

| Provider | What your server sends | Notes |
|---|---|---|
| OpenAI, Azure OpenAI, DeepSeek | `response.usage` and the model | A stream sends usage only with `stream_options.include_usage`, in a final chunk. A cancelled stream may never send it, and the hold then settles at the estimate. |
| Anthropic | `response.usage` and the model | In a stream, the usage in `message_delta` is cumulative. Send the last one. |
| Gemini 2.5, Vertex | `usageMetadata` and the model | Other Gemini versions may not price; send `cost` or `amount` for those. |
| AWS Bedrock | The Converse `usage` and the model | |
| OpenRouter | `usage`, which includes `cost` | ZeroSettle uses `cost` as given, before the catalog. |
| Vercel AI SDK | `result.usage` and the model id (`result.response.modelId`) | The usage has the same shape for every provider. The model id decides whether it prices. |
| Mistral, xAI, Groq, Together, Fireworks | `cost` or `amount` | Their model ids don't price today, so cost to serve is "Not measured" unless you send `cost`. |
| fal, Replicate, ElevenLabs, Runway, Luma, Stability | `amount`, in the action's unit (images, seconds, characters) | Their responses have no usable usage, so cost to serve is "Not measured" unless you send `cost`. |

## When ZeroSettle can't be reached

Your users should not be blocked by a problem on our side, so decide what your server does when it can't reach ZeroSettle.

- Set a short timeout, about 2 seconds.
- Optionally retry once with the same `idempotency_key`. A retry within 24 hours returns the first answer and spends nothing more.
- If ZeroSettle still can't be reached (a timeout, a network error or a `5xx`), follow the currency's "If ZeroSettle can't be reached" setting from the dashboard. It is on every response as `currency.offline`.
  - **Allow** (the default): let the request go ahead.
  - **Stop**: stop the request.
- A `4xx` is not an outage. It is an error in the request or the key, and the body carries the error code in `error`. Fix the request and don't retry it.
- A `429` is ZeroSettle's own rate limit. Wait for the `Retry-After` header before you retry.

When ZeroSettle can't be reached, nothing was spent. Keep the setting from the last answer you received for each currency, so you have it when the next call fails.

## When metering is paused

ZeroSettle can pause metering for an app, for example during an incident. Your code does not change. A spend answers `200` with `status: "allowed"`, `spent: 0`, `paused: true` and a `usage_id` that starts with `use_paused_`. Nothing is written or charged, so go ahead with the request.

```json
{
  "status": "allowed",
  "usage_id": "use_paused_4f9c2a1e",
  "currency": {"key": "credits", "name": "Credit", "plural": "Credits", "glyph": "sparkles", "offline": "allow"},
  "spent": 0,
  "held": false,
  "paused": true,
  "remaining": 318,
  "limit": 500,
  "resets_at": "2026-11-03T00:00:00Z",
  "plan": {"key": "pro", "name": "Pro", "kind": "tier"},
  "add_ons": [],
  "upgrade_available": null,
  "packs": null,
  "test_purchase": false
}
```

- Finish and undo on a `use_paused_` id answer `200` with `paused: true`, even after the app resumes. `currency` and `remaining` are `null`, because nothing was stored. Check for `null` before you test `remaining <= 0`: in JavaScript `null <= 0` is true.
- A request from before the pause finishes and undoes as usual.
- A key used while paused stores nothing, so the same key spends after the app resumes.
- If ZeroSettle cannot read the person's plan while paused, the answer is still `allowed`, with `plan: null`, `add_ons: []` and `remaining: 0`.
- `GET /v1/usage/` returns balances as usual with `paused: true`. The app read, `GET /v1/iap/entitlements/`, is unchanged. Balances stop moving until the app resumes.

## Test purchases

TestFlight, Xcode and App Review buy in Apple's sandbox, often with your live key. Those purchases give the person their plan and spend balances like any other, because access must work for App Review. The usage response carries `test_purchase: true` when the person's plan comes from one. The dashboard leaves that usage out of analytics unless you turn on "Include test purchases".
