## Sandbox Mode

ZeroSettle uses separate sandbox and live environments, determined entirely by your API key prefix:

- **Sandbox** (`zs_pk_test_`): Connects to Stripe's test environment. No real charges.
- **Live** (`zs_pk_live_`): Connects to Stripe's live environment. Real payments processed.

All SDK behavior is identical between sandbox and live — the only difference is which Stripe environment processes the payment. The dashboard has a **Sandbox** toggle in the top nav to switch between viewing sandbox and live data.

## Test Cards

Stripe provides test card numbers for simulating different payment outcomes. Use any future expiry date and any 3-digit CVC.

| Card Number | Outcome |
|---|---|
| `4242 4242 4242 4242` | Successful payment |
| `4000 0000 0000 0002` | Card declined |
| `4000 0000 0000 3220` | 3D Secure authentication required |
| `4000 0000 0000 9995` | Insufficient funds |

<Tip>
  For the full list of test cards (including specific error codes, international cards, and more), see [Stripe's testing documentation](https://docs.stripe.com/testing).
</Tip>

## End-to-End Test Flow

Walk through a complete purchase cycle in sandbox:

1. **Configure the SDK** with your sandbox key (`zs_pk_test_...`)
2. **Create a test product** on the dashboard (make sure you're in sandbox mode)
3. **Fetch products** — call `fetchProducts()` and verify your test product appears
4. **Trigger a purchase** — present the payment sheet or Safari checkout and pay with a test card
5. **Verify the transaction callback** — confirm your delegate receives `zeroSettleCheckoutDidComplete`
6. **Check entitlements** — call `restoreEntitlements()` and verify the product is active
7. **Verify in the dashboard** — switch to sandbox mode, open the **Transactions** tab, and confirm the transaction appears

```swift Swift
// 1. Configure with sandbox key
ZeroSettle.shared.configure(.init(
    publishableKey: "zs_pk_test_..."
))

// 2–3. identify() fetches products and restores entitlements
try await ZeroSettle.shared.identify(.user(id: testUser.id))

// 4. Trigger purchase (payment sheet or Safari)
// Use test card 4242 4242 4242 4242

// 5. Delegate callback fires
func zeroSettleCheckoutDidComplete(transaction: CheckoutTransaction) {
    print("Transaction: \(transaction.id)")
}

// 6. Verify entitlements
let entitlements = try await ZeroSettle.shared.restoreEntitlements()

```

```kotlin Kotlin
// 1. Configure with sandbox key
ZeroSettle.configure(context, ZeroSettleConfig(
    publishableKey = "zs_pk_test_..."
))

// 2–3. identify() fetches products and restores entitlements
ZeroSettle.identify(Identity.User(id = testUser.id))

// 4. Trigger purchase (payment sheet or Safari)
// Use test card 4242 4242 4242 4242

// 5. Observe purchase events via the events SharedFlow
ZeroSettle.events.collect { event ->
    if (event is ZeroSettleEvent.PurchaseSucceeded) {
        println("Transaction: ${event.transactionId}")
    }
}

// 6. Verify entitlements
val entitlements = ZeroSettle.restoreEntitlements().getOrThrow()
println("Active: ${entitlements.filter { it.isActive }}")
```

## Testing Subscriptions

Subscription lifecycle works the same in sandbox as in production:

- **Renewals** — App Store sandbox subscriptions renew on Apple's accelerated schedule: a monthly plan renews every few minutes, for a limited number of renewals. The resulting notifications reach ZeroSettle only when the sandbox server notification URL in App Store Connect points at ZeroSettle. It is the same URL as production; see [Webhooks & Server-Side](/iap/webhooks#setting-up-assn-v2). Web checkout subscriptions renew on their real schedule and cannot be fast-forwarded today.
- **Cancellation** — Users can cancel via the Stripe customer portal. The entitlement remains active until the end of the current billing period.
- **Refunds** — Issue refunds from the dashboard or directly in the Stripe dashboard. A full refund of the current billing period ends the subscription and access, and you receive `subscription.expired` and `transaction.refunded`. A partial refund is a credit only, and a refund of an earlier period leaves the subscription active. See [Refunds](/iap/event-webhooks#refunds).

<Note>
  To test your webhook handler without waiting for a renewal, use **Replay** (Dashboard, Integrations, Webhooks) to re-send a past delivery to your endpoint.
</Note>

## Resetting Sandbox Data

The dashboard provides three reset options under **Settings > Sandbox**. They act on the sandbox environment only.

### Reset to Live

Copies your live products and subscription configurations into the sandbox environment. Useful when your live catalog has diverged from sandbox.

### Reset to ASC

Re-syncs the sandbox from App Store Connect. Pulls the latest product metadata from your ASC catalog into sandbox.

### Clear All

Wipes all sandbox data, including transactions and entitlements. Products are preserved.

<Warning>
  **Clear All** is irreversible. You'll be asked to confirm before the reset is applied.
</Warning>

## Live mode test purchases and TestFlight

TestFlight builds, Xcode runs and App Review all buy in Apple's Sandbox, and they often use your app's **live** publishable key. ZeroSettle keeps these purchases in Live and marks them as test purchases. They are not moved to the sandbox environment.

What that means:

- The purchase is stored in **Live** and shows a **Test** badge in the dashboard.
- It **still unlocks access**, so App Review and your testers are never locked out.
- It is **excluded from revenue, MRR, charts, reports and active users** by default. Turn on **Include test purchases** in the dashboard sidebar to see it in those figures.
- Transaction and customer lists can show, hide or filter to test purchases only.
- Experiments and Autopilot always exclude test purchases.
- REST entitlement responses and event webhooks carry `is_test_purchase`. Ignore events with `is_test_purchase: true` when you count customers or revenue on your server. See [Event Webhooks](/iap/event-webhooks).
- The StoreKit sync response still carries `warning: "environment_mismatch"`. That is informational, not an error.

<Note>
  The iOS, Android and Flutter `Entitlement` types have no test-purchase flag, so your app cannot tell a test purchase apart from a real one. Read `is_test_purchase` on your server if you need to.
</Note>

A sandbox Apple ID used with a **sandbox** publishable key (`zs_pk_test_...`) stays in the sandbox environment, as before. Test purchases only describe Apple Sandbox purchases sent with a live key.

To test a TestFlight purchase end to end:

1. Install the TestFlight build, configured with your live key.
2. Sign in with a Sandbox Apple Account and buy a product.
3. In the dashboard, stay in Live mode and open **Transactions**. Turn on **Include test purchases** if the row is hidden.
4. Confirm the row shows the **Test** badge and the entitlement is active.

## Common Issues

| Symptom | Likely Cause | Fix |
|---|---|---|
| Products not loading | Wrong key or no sandbox products | Verify you're using `zs_pk_test_` and that products exist in sandbox mode on the dashboard |
| Payment sheet not appearing | Web checkout disabled for jurisdiction | Verify jurisdiction config on the dashboard. On iOS you can also check `isWebCheckoutEnabled` |
| Entitlements not updating after purchase | Webhook not delivered | Call `restoreEntitlements()` to force a refresh; check webhook delivery in the Stripe dashboard |
| "Web checkout disabled" error | Web checkout not enabled | Enable web checkout for the target jurisdiction on the dashboard |
| Transaction succeeds but delegate not called | Delegate not set | Ensure `ZeroSettle.shared.delegate = self` is set before triggering the purchase |
| StoreKit purchase from TestFlight or Xcode missing from Live figures | Test purchases are excluded by default | Turn on **Include test purchases** in the dashboard sidebar, or open Transactions and show test purchases |
