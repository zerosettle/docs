ZeroSettle acts as your Merchant of Record, which means **you never need to set up your own Stripe webhook endpoints** or handle raw payment events. ZeroSettle receives all payment lifecycle events from Stripe (and Apple), processes them automatically, and keeps your Transactions and Entitlements up to date.

Your app interacts with this system in three ways:

1. **Client-side** -- the SDK keeps the entitlements your app observes up to date (delegate callbacks on iOS, a `StateFlow` on Android)
2. **Server-side** -- your backend queries the Entitlements API to verify purchase status
3. **Event webhooks** -- ZeroSettle POSTs subscription lifecycle events to your server

<Note>
  This page covers the Stripe and Apple notifications ZeroSettle receives **on your
  behalf**. If you want ZeroSettle to notify **your** server when a subscription is
  purchased, renewed, cancelled or refunded, see [Event Webhooks](/iap/event-webhooks).
</Note>

## App Store Server Notifications

ZeroSettle also handles Apple's **App Store Server Notifications V2** (ASSN v2) for StoreKit subscription lifecycle events. If your app uses StoreKit purchases alongside web checkout, these notifications keep entitlements in sync automatically.

### Setting Up ASSN v2

<Tip>
  The quickest way: in the Dashboard, go to **Integrations → Webhooks**, open **App Store Server Notifications v2** and choose **ZeroSettle Managed**. ZeroSettle sets the URL in App Store Connect for you with your App Store Connect API key.
</Tip>

To set it yourself, configure the webhook URL in App Store Connect:

<Steps>
  <Step title="Open App Store Connect">
    Navigate to your app in [App Store Connect](https://appstoreconnect.apple.com).
  </Step>
  <Step title="Go to App Information">
    Select **App Information** from the sidebar under **General**.
  </Step>
  <Step title="Configure the webhook URL">
    Under **App Store Server Notifications**, set both the **Production Server URL** and the **Sandbox Server URL** to:

    ```
    https://api.zerosettle.io/v1/webhooks/appstore-notifications/
    ```

    The same URL serves both: ZeroSettle reads the environment from Apple's signed notification, so the sandbox URL needs no query parameter. Use the `api.zerosettle.io` host; `zerosettle.io` does not receive notifications.

    Select **Version 2** for the notification version.
  </Step>
</Steps>

<Note>
  Without these notifications, ZeroSettle learns about App Store renewals, expirations and refunds only when a customer opens the app. The dashboard shows a banner until they start arriving.
</Note>

### Handled Apple Notifications

ZeroSettle processes the following ASSN v2 notification types:

| Notification | What ZeroSettle Does |
|---|---|
| `REFUND` | Deactivates entitlement, marks transaction as refunded |
| `REVOKE` | Deactivates entitlement (family sharing revocation) |
| `DID_RENEW` | Extends entitlement expiry to new period end. Applies pending product changes from plan switches. |
| `EXPIRED` | Marks entitlement as expired and deactivates access |
| `DID_FAIL_TO_RENEW` | Marks entitlement as grace period or past due depending on subtype |
| `DID_CHANGE_RENEWAL_STATUS` | Handles auto-renew toggle (marks cancelled or reactivated) |
| `DID_CHANGE_RENEWAL_PREF` | Records pending product change for next renewal |
| `GRACE_PERIOD_EXPIRED` | Deactivates access after billing grace period ends |
| `RENEWAL_EXTENDED` | Extends entitlement expiry when Apple grants an extension |
| `SUBSCRIBED` | Creates transaction and entitlement for new subscriptions |
| `ONE_TIME_CHARGE` | Creates transaction and entitlement for one-time purchases |
| `OFFER_REDEEMED` | Records offer metadata on the entitlement |
| `REFUND_REVERSED` | Re-activates entitlement after a refund reversal |
| `REFUND_DECLINED` | Logged only (refund request was declined by Apple) |
| `EXTERNAL_PURCHASE_TOKEN` | Stores the external purchase token that Apple reports, so it can be matched to a purchase for external-purchase reporting. No entitlement change |

<Note>
  All Apple notifications are verified using JWS signature verification against Apple's Root CA certificate chain before processing. Duplicate notifications are automatically skipped via idempotency checks on the `notificationUUID`.
</Note>

<Note>
  As of **2026-04-27**, the following ASSN v2 events also mirror Apple's reported state onto the originating migration `Transaction` record's `storekit_status`, `storekit_apple_status`, and `storekit_subscription_end` fields — keeping migration trial-end resolution and dashboard analytics in sync without an SDK round-trip:

  - `DID_CHANGE_RENEWAL_STATUS` (subtypes `AUTO_RENEW_DISABLED`, `AUTO_RENEW_ENABLED`)
  - `EXPIRED`
  - `DID_FAIL_TO_RENEW` (default and `GRACE_PERIOD` subtype)
  - `REVOKE`
  - `REFUND`

  No SDK changes are required to consume this — the propagation is purely server-side.
</Note>

### Notification Forwarding

If your app needs to receive ASSN v2 notifications on your own server (e.g., for analytics or custom logic), you can configure **notification forwarding** in the ZeroSettle dashboard. When enabled, ZeroSettle processes the notification first, then forwards the original signed payload to your URL.

## How It Works

<Steps>
  <Step title="User completes checkout">
    The user pays via Apple Pay or card through the ZeroSettle checkout sheet. The SDK creates a PaymentIntent on ZeroSettle's backend.
  </Step>
  <Step title="Stripe sends a webhook to ZeroSettle">
    Stripe fires `payment_intent.succeeded` (or `checkout.session.completed` for session-based flows). ZeroSettle receives this at its webhook endpoint with signature verification.
  </Step>
  <Step title="ZeroSettle creates Transaction + Entitlement">
    The webhook handler creates an immutable `Transaction` record (the payment ledger entry) and an `Entitlement` (the user's access grant). For subscriptions, it also creates the Stripe subscription and tracks renewal state.
  </Step>
  <Step title="SDK updates client-side">
    The SDK polls for transaction completion and updates the local entitlement cache. The entitlements your app observes update to match.
  </Step>
  <Step title="Your backend verifies via API">
    At any point, your backend can query `GET /v1/iap/entitlements` to verify a user's purchase status server-side.
  </Step>
</Steps>

<Tip>
  Because ZeroSettle is the Merchant of Record, all webhook signature verification, idempotency handling, and retry logic is managed for you. Every webhook event is logged with an idempotency key to prevent duplicate processing.
</Tip>

## Server-Side Verification

For server-side purchase verification (e.g., unlocking content from your API, validating access in a game server, or gating API features), query the Entitlements API.

### What the publishable key can and cannot do

The key in the examples below is your **publishable** key. It ships inside your app, so treat it as public: anyone who extracts it from your app can call these endpoints with any `user_id` and read that user's entitlements.

- Reading entitlements with it is fine for **UI** decisions, such as showing or hiding a paywall.
- Do not grant server-side value (credits, downloads, API access, account changes) on the strength of a client claim, or of an entitlement read made with a key the client holds.
- For server-side value, drive your records from the signed [event webhooks](/iap/event-webhooks) (verify the signature, then act). Use the Entitlements API from your server only to double-check a user you already know about.
- Your **secret** key (`zs_sk_...`) must stay on your server. Only [Get Migration Cohort](/api-reference/endpoint/migration-cohort) uses it today.

### Query by User ID

```bash
curl --request GET \
  --url 'https://api.zerosettle.io/v1/iap/entitlements/?user_id=your_user_id' \
  --header 'X-ZeroSettle-Key: zs_pk_live_...'
```

### Query by Email

Email lookup is deprecated and narrow. It matches only legacy email-only checkouts, where the purchase has no `user_id` attached. It does **not** find a user your app identified with a `user_id`, and it does not find [anonymous users](/iap/user-identity#option-3-anonymous-users) from the SDK: those carry a generated UUID as their `user_id`, so look them up by that UUID.

```bash
curl --request GET \
  --url 'https://api.zerosettle.io/v1/iap/entitlements/?email=user@example.com' \
  --header 'X-ZeroSettle-Key: zs_pk_live_...'
```

### Response Format

```json
{
  "entitlements": [
    {
      "id": "txn_abc123",
      "product_id": "premium_monthly",
      "product_type": "auto_renewable",
      "source": "web_checkout",
      "status": "active",
      "is_active": true,
      "expires_at": null,
      "purchased_at": "2025-03-14T12:00:00Z",
      "will_renew": true,
      "is_trial": false,
      "trial_ends_at": null,
      "cancelled_at": null,
      "is_test_purchase": false
    }
  ],
  "pending_actions": []
}
```

Only entitlements that still grant access are returned (`active`, `cancelled`, `grace_period`, `past_due`). Expired and paused ones are not in the list. `product_type` is one of `consumable`, `non_consumable`, `non_renewing` or `auto_renewable`. `pending_actions` lists follow-up steps for the app to show, such as cancelling an old store subscription after Switch & Save, and is empty when there are none.

`is_test_purchase` is `true` when Apple processed the purchase as a sandbox purchase (TestFlight, App Review or Xcode) but your app sent it with a live ZeroSettle key. The entitlement still grants access, so reviewers and testers are never locked out. Skip these when you count customers or revenue on your side.

### Server-Side Verification Examples

<CodeGroup>

```javascript Node.js
const response = await fetch(
  `https://api.zerosettle.io/v1/iap/entitlements/?user_id=${userId}`,
  {
    headers: {
      'X-ZeroSettle-Key': process.env.ZEROSETTLE_KEY,
    },
  }
);

const { entitlements } = await response.json();
const hasPremium = entitlements.some(
  (e) => e.product_id === 'premium_monthly' && e.is_active
);

if (!hasPremium) {
  return res.status(403).json({ error: 'Premium subscription required' });
}
```

```python Python
import requests

response = requests.get(
    "https://api.zerosettle.io/v1/iap/entitlements/",
    params={"user_id": user_id},
    headers={"X-ZeroSettle-Key": os.environ["ZEROSETTLE_KEY"]},
)

entitlements = response.json()["entitlements"]
has_premium = any(
    e["product_id"] == "premium_monthly" and e["is_active"]
    for e in entitlements
)

if not has_premium:
    raise PermissionError("Premium subscription required")
```

```go Go
req, _ := http.NewRequest("GET",
    "https://api.zerosettle.io/v1/iap/entitlements/?user_id="+userID, nil)
req.Header.Set("X-ZeroSettle-Key", os.Getenv("ZEROSETTLE_KEY"))

resp, err := http.DefaultClient.Do(req)
// parse resp.Body for entitlements...
```

</CodeGroup>

<Note>
  These endpoints authenticate with your **publishable key** (`zs_pk_live_...` or `zs_pk_test_...`) via the `X-ZeroSettle-Key` header -- the same key you use in the SDK. Use `zs_pk_test_...` for sandbox queries and `zs_pk_live_...` for production. The one server-to-server endpoint, [Get Migration Cohort](/api-reference/endpoint/migration-cohort), takes a secret key instead.
</Note>

### Transaction History

For a full history of a user's transactions (including failed and refunded ones), use the transaction history endpoint:

```bash
curl --request GET \
  --url 'https://api.zerosettle.io/v1/iap/transaction-history/?user_id=your_user_id&limit=50' \
  --header 'X-ZeroSettle-Key: zs_pk_live_...'
```

This returns the user's transactions with the statuses `completed`, `pending`, `processing`, `failed` and `refunded` (a disputed transaction is reported as `refunded`), including consumed consumables, expired subscriptions, and refunds. Abandoned checkout sessions are not returned. The `limit` parameter defaults to 50 (max 100); there is no cursor.

## Client-Side Updates

The SDK tells your app when entitlements change on the device: a delegate on iOS, a `StateFlow` on Android, a hook in React Native and a stream in Flutter. Updates follow purchases, restores, refunds, and subscription renewals that the SDK sees.

### Delegate Callbacks

<CodeGroup>

```swift Swift
class PurchaseManager: ZeroSettleDelegate {
    init() {
        ZeroSettle.shared.delegate = self
    }

    func zeroSettleEntitlementsDidUpdate(_ entitlements: [Entitlement]) {
        // Fires after any entitlement change:
        // - Purchase completed
        // - Subscription renewed
        // - Refund processed
        // - Restore completed
        for entitlement in entitlements {
            if entitlement.isActive {
                unlockFeature(entitlement.productId)
            } else {
                lockFeature(entitlement.productId)
            }
        }
    }
}
```

```kotlin Kotlin
// Android has no delegate. Collect the entitlements flow instead.
class PurchaseManager(scope: CoroutineScope) {
    init {
        scope.launch {
            ZeroSettle.entitlements.collect { entitlements ->
                for (entitlement in entitlements) {
                    if (entitlement.isActive) {
                        unlockFeature(entitlement.productId)
                    } else {
                        lockFeature(entitlement.productId)
                    }
                }
            }
        }
    }
}
```

```tsx React Native
import { useZeroSettleEvents } from 'react-native-zerosettle';

function PurchaseManager() {
  useZeroSettleEvents({
    onEntitlementsDidUpdate: (entitlements) => {
      for (const entitlement of entitlements) {
        if (entitlement.isActive) {
          unlockFeature(entitlement.productId);
        } else {
          lockFeature(entitlement.productId);
        }
      }
    },
  });

  return null;
}
```

```dart Flutter
ZeroSettle.instance.entitlementUpdates.listen((entitlements) {
  for (final entitlement in entitlements) {
    if (entitlement.isActive) {
      unlockFeature(entitlement.productId);
    } else {
      lockFeature(entitlement.productId);
    }
  }
});
```

</CodeGroup>

<Note>
  Entitlement updates are triggered by SDK operations (purchases, restores). They are **not** pushed from the backend in real-time via WebSocket or push notification. For server-authoritative access control, use signed [event webhooks](/iap/event-webhooks) and the Entitlements API on your backend.
</Note>

### Reactive UI Observation

You can also observe entitlements reactively in your UI framework:

<CodeGroup>

```swift SwiftUI
struct ContentView: View {
    // ZeroSettle is @Observable — reading it in `body` is tracked automatically.
    private var iap: ZeroSettle { .shared }

    var body: some View {
        if iap.entitlements.contains(where: { $0.isActive }) {
            PremiumContent()
        } else {
            UpgradePrompt()
        }
    }
}
```

```kotlin Jetpack Compose
@Composable
fun ContentScreen() {
    val entitlements by ZeroSettle.entitlements.collectAsState()

    if (entitlements.any { it.isActive }) {
        PremiumContent()
    } else {
        UpgradePrompt()
    }
}
```

```tsx React Native
import { useState } from 'react';
import { useZeroSettleEvents, Entitlement } from 'react-native-zerosettle';

function ContentScreen() {
  const [entitlements, setEntitlements] = useState<Entitlement[]>([]);

  useZeroSettleEvents({
    onEntitlementsDidUpdate: setEntitlements,
  });

  const hasAccess = entitlements.some((e) => e.isActive);

  return hasAccess ? <PremiumContent /> : <UpgradePrompt />;
}
```

```dart Flutter
StreamBuilder<List<Entitlement>>(
  stream: ZeroSettle.instance.entitlementUpdates,
  builder: (context, snapshot) {
    final hasAccess = snapshot.data?.any((e) => e.isActive) ?? false;
    return hasAccess ? PremiumContent() : UpgradePrompt();
  },
)
```

</CodeGroup>

## Stripe Webhook Events

ZeroSettle processes the following Stripe webhook events automatically. You do **not** need to handle these yourself.

<AccordionGroup>
  <Accordion title="Payment Events">
    | Event | What ZeroSettle Does |
    |-------|---------------------|
    | `payment_intent.succeeded` | Marks transaction as succeeded, creates Identity + Entitlement. For subscriptions, creates the Stripe subscription and handles plan upgrades (cancels old subscription with proration). |
    | `payment_intent.processing` | Moves transaction from `pending` to `processing`, freeing the deduplication slot so the user can retry if needed. |
    | `payment_intent.payment_failed` | Marks the pending transaction as `failed`. |
    | `payment_intent.canceled` | Marks the pending transaction as `failed` to free the dedup slot. |
  </Accordion>

  <Accordion title="Checkout Session Events">
    | Event | What ZeroSettle Does |
    |-------|---------------------|
    | `checkout.session.completed` | Routes to IAP checkout handler if `payment_status=paid`. Creates Transaction + Entitlement. |
    | `checkout.session.expired` | Marks pending transaction as `failed` when the checkout session expires without payment. |
  </Accordion>

  <Accordion title="Subscription Lifecycle Events">
    | Event | What ZeroSettle Does |
    |-------|---------------------|
    | `customer.subscription.updated` | Handles cancellation (`cancel_at_period_end`), pause/resume, and status changes. Entitlement stays active until period end on cancellation. |
    | `customer.subscription.deleted` | Deactivates the entitlement when the subscription is fully terminated. |
    | `customer.subscription.paused` | Marks entitlement as paused. Access is suspended until resumed. |
    | `customer.subscription.resumed` | Reactivates a paused entitlement. |
    | `customer.subscription.trial_will_end` | Logs upcoming trial expiration (~3 days before). Used for Switch & Save migrations with aligned trial periods. |
  </Accordion>

  <Accordion title="Invoice Events">
    | Event | What ZeroSettle Does |
    |-------|---------------------|
    | `invoice.paid` | Creates Transaction records for subscription renewals and proration charges. Extends entitlement expiry on renewal. Skips initial `subscription_create` invoices (handled by checkout flow). |
    | `invoice.payment_failed` | Logs renewal failure context. Entitlement status is handled by `customer.subscription.updated` (moves to `past_due`). |
    | `invoice.voided` | Handles voided invoices for paused subscriptions. |
  </Accordion>

  <Accordion title="Refund & Dispute Events">
    | Event | What ZeroSettle Does |
    |-------|---------------------|
    | `charge.refunded` | Marks transaction as `refunded`, deactivates all linked entitlements. |
    | `charge.dispute.created` | Marks transaction as `disputed`, revokes all linked entitlements. ZeroSettle handles evidence submission as MoR. |
    | `charge.dispute.updated` | Logs dispute status changes. |
    | `charge.dispute.closed` | Records dispute outcome (won/lost). |
    | `charge.dispute.funds_withdrawn` | Logs fund withdrawal. |
    | `charge.dispute.funds_reinstated` | Re-activates entitlements if dispute is won and funds are returned. |
  </Accordion>

  <Accordion title="Setup & Account Events">
    | Event | What ZeroSettle Does |
    |-------|---------------------|
    | `setup_intent.succeeded` | Confirms trial subscription card setup. Finalizes the trial transaction. |
    | `setup_intent.setup_failed` | Marks trial transaction as failed if card setup fails. |
    | `account.application.deauthorized` | Clears stale Stripe references when a connected account revokes platform access. |
  </Accordion>
</AccordionGroup>

### BYOS (Bring Your Own Stripe)

If you use [BYOS mode](/iap/stripe-catalog) with your own Stripe account connected via OAuth, ZeroSettle still receives and processes all webhook events through the same endpoint. Stripe routes Connect webhooks to the platform automatically. You do not need to configure a separate webhook endpoint on your connected account.

<Warning>
  Do not configure your own webhook endpoint for the same events on your connected Stripe account. Duplicate processing can cause entitlement conflicts.
</Warning>

## Best Practices

<AccordionGroup>
  <Accordion title="Use server-side verification for access control">
    For content gating on your backend (API access, downloadable content, server-side features), do not trust client-side state or a claim sent by the app. Drive access from signed [event webhooks](/iap/event-webhooks), and check the REST API from your server when you need to confirm a user. The SDK cache is convenient for UI but should not be the source of truth for authorization decisions.
  </Accordion>

  <Accordion title="Call restoreEntitlements() on app launch">
    The SDK's entitlement cache is in-memory only and is cleared when the app process terminates. Call `restoreEntitlements()` on every app launch to rehydrate the user's entitlements from the server.
  </Accordion>

  <Accordion title="Handle the empty entitlements case">
    Entitlements will be empty if no purchases have been made. Always handle this case gracefully in your UI and server-side logic.
  </Accordion>

  <Accordion title="Don't build your own Stripe webhook handler">
    ZeroSettle handles all Stripe webhook processing, including signature verification, idempotency, and retry logic. Building a parallel webhook handler will cause duplicate entitlement creation and state conflicts.
  </Accordion>
</AccordionGroup>
