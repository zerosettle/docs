<Info>
  **Your server pages.** This page covers events ZeroSettle sends to your server. To verify a user's access from your backend, or to set up App Store Server Notifications and forwarding, see [Notifications and Server-Side Verification](/iap/webhooks).
</Info>

ZeroSettle can POST an event to your server whenever a subscription changes — a
purchase, a renewal, a cancellation, a refund. Use these to keep your own database in
sync, trigger emails, or notify your team, without polling our API.

<Note>
  This page covers events **we send to you**. For the Stripe and App Store notifications
  that ZeroSettle receives and handles on your behalf, see
  [Notifications and Server-Side Verification](/iap/webhooks) — you do not need to handle those yourself.
</Note>

## Setting up an endpoint

<Steps>
  <Step title="Add your endpoint">
    In the Dashboard, go to **Integrations → Webhooks** and add your HTTPS URL.
  </Step>
  <Step title="Copy the signing secret">
    It is shown **once**. If you lose it, use **Rotate** to generate a new one.
  </Step>
  <Step title="Choose your events">
    Subscribe to everything (`*`) or pick a subset. `*` includes event types added in
    future, so your handler must tolerate a `type` it does not recognise.
  </Step>
</Steps>

<Warning>
  Endpoints are **per environment**. A live endpoint receives nothing from sandbox
  testing. If you want events while testing, add a separate endpoint in sandbox mode.
</Warning>

## Event types

<AccordionGroup>
  <Accordion title="Subscription lifecycle">
    | Event | When it fires |
    |---|---|
    | `subscription.purchased` | A new subscription, non-consumable or non-renewing purchase was granted (first grant) |
    | `subscription.renewed` | An existing subscription renewed for a new period. Carries the new period's `expires_at` and status `active` |
    | `subscription.cancelled` | Auto-renew was turned off. **Access continues until period end** |
    | `subscription.expired` | The subscription ended and access was revoked. Also sent when a full refund of the current billing period ends the subscription |
    | `subscription.billing_issue` | A renewal payment failed. See [Billing problems](#billing-problems) |
    | `subscription.recovered` | Recovered from a billing issue and is active again |
    | `subscription.product_changed` | The subscriber switched product (upgrade, downgrade, or migration) |
  </Accordion>

  <Accordion title="Trials">
    | Event | When it fires |
    |---|---|
    | `trial.started` | A free trial began |
    | `trial.converted` | A free trial converted to a paid subscription |
  </Accordion>

  <Accordion title="Payments">
    | Event | When it fires |
    |---|---|
    | `transaction.refunded` | A payment was refunded. See [Refunds](#refunds) |
  </Accordion>

  <Accordion title="Switch & Save eligibility">
    | Event | When it fires |
    |---|---|
    | `migration.eligible` | A store subscriber became eligible for the Switch & Save offer |
    | `migration.ineligible` | A subscriber is no longer eligible |
    | `migration.completed` | A subscriber completed the migration to web billing |

    See [Switch & Save](/iap/switch-and-save) for the flow these describe.
  </Accordion>

  <Accordion title="Identity">
    | Event | When it fires |
    |---|---|
    | `identity.reconciled` | One customer id was merged into another: by your server, a link token, a support merge in the dashboard or Restore Purchases. It fires on every merge, including one that moved nothing. See [Identity reconciled](#identity-reconciled) |
  </Accordion>

  <Accordion title="Granted access">
    | Event | When it fires |
    |---|---|
    | `access_grant.started` | A customer was given free access to a product they had no granted access to |
    | `access_grant.extended` | A customer who already had granted access to the product was given more, queued behind it |
    | `access_grant.ending_soon` | Granted access ends within 3 days. Sent once, for the last grant of a run |
    | `access_grant.ended` | Granted access ran out. Not sent when another grant carries on from it, or when a revoke already ended it |
    | `access_grant.revoked` | A grant was revoked, from the dashboard or with the [revoke endpoint](/api-reference/endpoint/revoke-access-grant) |

    See [Access grant events](#access-grant-events).
  </Accordion>
</AccordionGroup>

<Note>
  The `migration.*` events use a different envelope from the other events. See
  [Switch & Save events](#switch-and-save-events).
</Note>

<Tip>
  `subscription.cancelled` and `subscription.expired` are easy to confuse. Cancelled means
  they turned off auto-renew and **still have access**. Expired means access has ended.
  Revoke on `expired`, not on `cancelled`.
</Tip>

## When events are sent

We do not repeat an event for a change you have already been told about. A single
cancellation produces one `subscription.cancelled`, and a single expiry produces one
`subscription.expired`, even when more than one system reports the same change. Retries
of a delivery still repeat the same event, so keep deduplicating (see [Deduplicating](#deduplicating)).

### Renewals

`subscription.renewed` carries the new period's `expires_at` and status `active`. If the
renewal follows a failed payment, you also receive `subscription.recovered` (status
`active`). It normally arrives first, but treat both as "grant access" and do not depend
on the order.

### Billing problems

`subscription.billing_issue` means a renewal payment failed. What you see depends on the
rail.

**Web checkout.** The status is `past_due`. `expires_at` shows the end of the new billing
period, because Stripe starts the period when it creates the renewal invoice, before the
payment succeeds. The customer keeps access while Stripe retries. If payment succeeds you
receive `subscription.recovered` and then `subscription.renewed`. What happens after the
last retry is set by the failed-payment settings in your Stripe account: if it cancels the
subscription or marks it unpaid, you receive `subscription.expired`. If it leaves the
subscription `past_due`, no further event is sent.

**App Store.** If Billing Grace Period is enabled for the app in App Store Connect, the
status is `grace_period` and `expires_at` is Apple's grace end date, so access continues
until then. Billing Grace Period is opt-in, set to 3, 16 or 28 days (weekly plans cap at
6). Without it, Apple stops service while it retries billing, the status is `past_due`, and
`expires_at` is the end of the period that was paid.

### Refunds

A payment produces **one** `transaction.refunded`. Its `id` is `evt_txn_<transaction id>`,
so a second refund on the same payment (for example a partial refund followed by the rest)
sends no further event.

- **Full refund of the current billing period.** The subscription and access end. You
  receive `subscription.expired` and `transaction.refunded`, in either order. Revoke on
  `expired`, and treat `transaction.refunded` as the payment record. For web checkout we
  also cancel the Stripe subscription, so the customer is not billed again.
- **Partial refund.** This is a credit only. You receive `transaction.refunded`, and the
  subscription and access are unchanged.
- **Refund of an earlier period** while a later period is paid and active. You receive only
  `transaction.refunded`, and the subscription stays active.

The same rule, current period versus earlier period, applies to App Store refunds.

## Payload

Subscription, trial, `transaction.refunded` and `identity.reconciled` events share one envelope shape
(`id`, `type`, `created`, `environment`, `project_id`, `data`), but the `data` block differs by event.
`identity.reconciled` has no `external_user_id`: see [Identity reconciled](#identity-reconciled).
The `migration.*` events are different again: see [Switch & Save events](#switch-and-save-events).
Subscription and trial events:

```json
{
  "id": "evt_12345",
  "type": "subscription.purchased",
  "created": "2026-09-10T03:22:24.728189+00:00",
  "environment": "live",
  "project_id": 85,
  "data": {
    "external_user_id": "firebase-uid-or-anonymous-uuid",
    "product_id": "com.yourapp.premium.monthly",
    "source": "web_checkout",
    "is_test_purchase": false,
    "entitlement": {
      "status": "active",
      "expires_at": "2026-10-10T03:22:24+00:00",
      "will_renew": true,
      "is_trial": false
    }
  }
}
```

`transaction.refunded` carries a transaction block instead of an entitlement one:

```json
{
  "id": "evt_txn_67890",
  "type": "transaction.refunded",
  "created": "2026-09-10T03:22:24.728189+00:00",
  "environment": "live",
  "project_id": 85,
  "data": {
    "external_user_id": "firebase-uid-or-anonymous-uuid",

      "id": 14050487,
      "amount_cents": 799,
      "refund_amount_cents": 799,
      "status": "refunded"
    }
  }
}
```

### Switch and Save events

`migration.eligible`, `migration.ineligible` and `migration.completed` do **not** use the
envelope above. They have no `id`, `type`, `created` or `environment`. They carry
`event_type`, `project_id`, `is_sandbox` and `fired_at`, and the same value as
`event_type` is in the `X-ZeroSettle-Event-Type` header. Read the header or `event_type`
to route them.

```json
{
  "event_type": "migration.eligible",
  "project_id": 85,
  "is_sandbox": false,
  "fired_at": "2026-09-10T03:22:24.728189+00:00",
  "source": "assn",
  "data": {
    "external_user_id": "firebase-uid-or-anonymous-uuid",
    "product_id": "com.yourapp.premium.monthly",
    "is_eligible": true,
    "reason": null,
    "days_subscribed": 21,
    "rollout_bucket": 42,
    "eligible_at": null
  }
}
```

`migration.ineligible` has the same shape with `is_eligible` set to `false` and a `reason`
such as `tenure_too_short`, `tenure_too_long`, `outside_rollout`, `blocking_status`,
`no_active_sub`, `campaign_disabled`, `not_checkout_ready` or `product_not_eligible`.
`reason` and `eligible_at` are `null` when the user is eligible. `source` says what
triggered the check (for example `assn` or `claim`) and may be absent.
`migration.completed`:

```json
{
  "event_type": "migration.completed",
  "project_id": 85,
  "is_sandbox": false,
  "fired_at": "2026-09-10T03:22:24.728189+00:00",
  "data": {
    "external_user_id": "firebase-uid-or-anonymous-uuid",
    "storekit_product_id": "com.yourapp.premium.monthly",
    "web_product_id": "com.yourapp.premium.monthly.web",
    "web_transaction_id": 14050487
  }
}
```

Because there is no body `id`, deduplicate these on the `X-ZeroSettle-Idempotency-Key`
header, which is stable for one state change. The two eligibility events fire when the
state flips, not on every check.

### Identity reconciled

`identity.reconciled` fires when one customer id is merged into another, see [Guest to Account](/iap/guest-to-account). It fires once per merge, and on **every** merge that happens: a merge that moved no purchases still sends it, with `moved` counts of `0`. A reconcile that only moves a guest's analytics (the guest id has no customer record) is not a merge and sends no event. A refused reconcile sends none either.

```json
{
  "id": "evt_reconciled_4821",
  "type": "identity.reconciled",
  "created": "2026-10-23T14:05:11.402918+00:00",
  "environment": "live",
  "project_id": 85,
  "data": {
    "reconciliation_id": 4821,
    "from_user_id": "3f1c9c52-8f5e-4a52-9d9c-0f0b6f1a7c11",
    "into_user_id": "user_8472",
    "actor": "secret_key",
    "moved": {
      "transactions": 2,
      "entitlements": 1
    }
  }
}
```

| Field | Notes |
|---|---|
| `data.reconciliation_id` | The id of the reconciliation record. Same as `reconciliation_id` in the reconcile endpoint response |
| `data.from_user_id` | The id that was merged away. Later events and reads under it forward to `into_user_id`. `null` when the source had no external id (an email-only restore) |
| `data.into_user_id` | The id that kept the purchases |
| `data.actor` | Who asked for the merge: `secret_key`, `link_token`, `dashboard_user`, `restore_purchases`, `identity_link` or `system`. `identity_link` is the SDK folding a `zs_anon_` guest id into the account at sign-in, and `from_user_id` is then that `zs_anon_` id. Tolerate other values |
| `data.moved.transactions` | Transactions that moved |
| `data.moved.entitlements` | Entitlements that moved |

<Warning>
  **This event has no `data.external_user_id`.** The subscription, trial and refund events all carry it, so a catch-all handler that routes on `event.data.external_user_id` before it looks at `event.type` will break on this event. Branch on `type` first. The ids are `data.from_user_id` and `data.into_user_id`.
</Warning>

On this event, make your own records for `from_user_id` point at `into_user_id`, and do not treat the move as a new purchase. No `subscription.purchased` is sent for a subscription that moved. Restore Purchases sends `identity.reconciled` too, not `subscription.purchased`.

<CodeGroup>

```javascript Node.js
// Inside your verified, deduplicated handler (see Handling events)
if (event.type === 'identity.reconciled') {
  const { from_user_id, into_user_id, moved } = event.data;

  // Re-point anything you keyed on the guest id. from_user_id can be null.
  if (from_user_id) {
    await db.users.repointId({ from: from_user_id, to: into_user_id });
  }

  // A merge that moved nothing still arrives, with zero counts.
  if (moved.entitlements > 0) {
    await refreshAccess(into_user_id);
  }
}
```

```python Python
# Inside your verified, deduplicated handler (see Handling events)
if event["type"] == "identity.reconciled":
    data = event["data"]
    from_id = data["from_user_id"]  # can be None
    into_id = data["into_user_id"]

    # Re-point anything you keyed on the guest id.
    if from_id:
        db.repoint_user_id(old=from_id, new=into_id)

    # A merge that moved nothing still arrives, with zero counts.
    if data["moved"]["entitlements"] > 0:
        refresh_access(into_id)
```

</CodeGroup>

### Access grant events

The `access_grant.*` events tell you when free access starts, is queued, is about to run out, ends or is cancelled. They share the usual envelope (`id`, `type`, `created`, `environment`, `project_id`, `data`):

```json
{
  "id": "evt_access_grant_912_started",
  "type": "access_grant.started",
  "created": "2026-10-31T09:14:02.118223+00:00",
  "environment": "live",
  "project_id": 85,
  "data": {
    "external_user_id": "user_8472",
    "product_id": "com.yourapp.premium.monthly",
    "grant_id": 912,
    "origin": "api",
    "reason": "apology",
    "starts_at": "2026-10-31T09:14:02.101114+00:00",
    "ends_at": "2026-11-30T09:14:02.101114+00:00",
    "access_ends_at": "2026-11-30T09:14:02.101114+00:00",
    "reward_id": null
  }
}
```

| Field | Notes |
|---|---|
| `id` | `evt_access_grant_<grant_id>_<event name>`, stable per grant and event. Use it to deduplicate |
| `data.external_user_id` | The customer's id in your app |
| `data.product_id` | Your canonical product reference id |
| `data.grant_id` | The grant's id, the same one the [grant endpoints](/api-reference/endpoint/create-access-grant) return as `id` |
| `data.origin` | `manual`, `api` or `referral_reward` |
| `data.reason` | `support`, `comp`, `apology`, `promotion`, `referral` or `other` |
| `data.starts_at` | When this grant's access starts. Later than the event for a grant queued behind another |
| `data.ends_at` | When this grant's own access ends. `null` when it has no end |
| `data.access_ends_at` | When the customer's granted access to the product ends, counting every grant that runs back to back. `null` **only** when the access has no end. Otherwise it is the time access ends, or for `access_grant.revoked` and `access_grant.ended`, the time it stopped |
| `data.reward_id` | Set when the grant came from a reward, otherwise `null` |

`ending_soon` and `ended` are sent by a job that runs every 15 minutes, so they can arrive a little after the time they describe. Access itself ends on time and does not wait for the event. They are delivered at least once, so deduplicate on `id`.

These events say nothing about paid purchases. A customer whose granted access ended can still have access through a subscription, so check [`access`](/api-reference/endpoint/get-entitlements#access) before you lock anything.

### Field reference

| Field | Notes |
|---|---|
| `id` | Unique and stable per event, the same for every endpoint you have. It is **not** the `X-ZeroSettle-Event-Id` header. Use it to deduplicate |
| `type` | The event type. **Note the field is `type`, not `event_type`** |
| `environment` | `live` or `sandbox` |
| `data.external_user_id` | Whatever you passed to `identify(_:)`. For anonymous users this is a generated UUID that will not match a user in your system. Not present on `identity.reconciled` |
| `data.product_id` | Your canonical product reference id |
| `data.source` | The rail the subscription is on: `web_checkout`, `store_kit` or `play_store`. It is also set on `subscription.cancelled` and `subscription.expired`. It is `null` only for an entitlement granted manually from the dashboard that has never been on a rail — see below. On `transaction.refunded` it is the raw payment source, which can also be `play_billing` or `play_billing_external` for Google Play |
| `data.transaction.id` | On `transaction.refunded`: ZeroSettle's internal transaction number (an integer). Not a Stripe or Apple id |
| `data.is_test_purchase` | `true` when Apple processed the purchase as a sandbox purchase (TestFlight, App Review or Xcode) but your app sent it with a live key. Ignore these events for billing and analytics. Always present, `false` for real purchases |
| `data.entitlement.status` | Current status — see below |
| `data.entitlement.expires_at` | When the current period ends. During a billing problem the meaning depends on the rail — see [Billing problems](#billing-problems) |
| `data.entitlement.will_renew` | Whether it is set to auto-renew |
| `data.entitlement.is_trial` | Whether the current period is a trial |

### `source` values

| Value | Meaning |
|---|---|
| `web_checkout` | Purchased through ZeroSettle web checkout |
| `store_kit` | Purchased through Apple StoreKit (note the underscore) |
| `play_store` | Purchased through Google Play |

During a Switch & Save migration a user can briefly be active on both web and store. In
that window we report `web_checkout`, because that is the direction of travel.

### `entitlement.status` values

| Value | Has access? |
|---|---|
| `active` | Yes |
| `cancelled` | **Yes** — auto-renew off, paid through period end |
| `grace_period` | **Yes** — App Store payment failed, access continues until the grace end date in `expires_at` |
| `past_due` | **Depends on the rail.** Web checkout: yes, Stripe is retrying. App Store without Billing Grace Period: no, Apple has stopped service and `expires_at` is the end of the paid period |
| `expired` | No |
| `paused` | No |

<Warning>
  Do not gate access on `status == "active"` alone. `cancelled` and `grace_period` mean the
  user holds access, and `past_due` does on web checkout. Check `expires_at` as well.
</Warning>

## Delivery

Every request carries these headers:

| Header | Purpose |
|---|---|
| `X-ZeroSettle-Event-Id` | Id of this delivery to this endpoint: 32 hex characters, the same on every retry and replay of it. It is not the body `id` |
| `X-ZeroSettle-Event-Type` | The event type. Same as the body's `type` (or `event_type` for `migration.*`) |
| `X-ZeroSettle-Idempotency-Key` | Stable key for the underlying state change |
| `X-ZeroSettle-Signature` | `t=<unix_ts>,v1=<hmac_sha256_hex>` |

The request also sets `User-Agent: ZeroSettle-Webhooks/1.0` and `Content-Type: application/json`.

### Deduplicating

Two ids are in play, and they are not the same value:

- The body `id` (`evt_...`) names the event. It is identical for every endpoint you have and for every retry. Deduplicate on it.
- `X-ZeroSettle-Event-Id` names one delivery to one endpoint. It is the same on retries and replays, but it differs per endpoint and never equals the body `id`.

For `migration.*` events, which have no body `id`, use `X-ZeroSettle-Idempotency-Key`.

Return any `2xx` to acknowledge. We time out after 10 seconds, so acknowledge first and
do your work asynchronously.

### Retries

A delivery is tried up to **6 times**: the first attempt, then 5 retries. Each retry
waits after the previous failure: **2 minutes, 10 minutes, 1 hour, 6 hours, 24 hours**.
After the sixth failed attempt the delivery is marked failed. A timeout, a connection
error, a `5xx`, `408` or `429` is retried. Any other `4xx` is treated as permanent and not
retried.

Retries are sent only for deliveries less than 48 hours old, so a delivery that is still
failing after that is not sent again on its own. Full delivery history and a **Replay**
button are in the Dashboard. A replay sends the delivery again whatever its age.

<Tip>
  Retries mean your handler must be idempotent. Deduplicate on the body `id` (see
  [Deduplicating](#deduplicating)).
</Tip>

## Verifying signatures

The signature is `t=<timestamp>,v1=<hex>`, where the HMAC-SHA256 is computed over
`{timestamp}.{raw_body}` using your signing secret. Verify against the **raw** body,
before any JSON parsing — re-serialising will change the bytes and break the check.

<CodeGroup>

```javascript Node.js
const crypto = require('crypto');

function verify(rawBody, header, secret, toleranceSeconds = 300) {
  const parts = Object.fromEntries(header.split(',').map(p => p.split('=')));
  const expected = crypto
    .createHmac('sha256', secret)
    .update(`${parts.t}.${rawBody}`)
    .digest('hex');

  // Reject stale timestamps to blunt replay attacks
  if (Math.abs(Date.now() / 1000 - Number(parts.t)) > toleranceSeconds) return false;

  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(parts.v1)
  );
}
```

```python Python
import hashlib, hmac, time

def verify(raw_body: bytes, header: str, secret: str, tolerance: int = 300) -> bool:
    parts = dict(p.split('=', 1) for p in header.split(',') if '=' in p)
    expected = hmac.new(
        secret.encode(),
        f"{parts['t']}.{raw_body.decode()}".encode(),
        hashlib.sha256,
    ).hexdigest()

    if abs(time.time() - int(parts['t'])) > tolerance:
        return False

    return hmac.compare_digest(expected, parts['v1'])
```

</CodeGroup>

<Warning>
  Compare with a constant-time function (`timingSafeEqual`, `hmac.compare_digest`).
  A plain `==` leaks timing information.
</Warning>

## Handling events

```javascript
app.post('/webhooks/zerosettle', express.raw({ type: 'application/json' }), (req, res) => {
  if (!verify(req.body.toString(), req.get('X-ZeroSettle-Signature'), SECRET)) {
    return res.sendStatus(401);
  }

  const event = JSON.parse(req.body.toString());

  // Acknowledge immediately — we time out at 10s
  res.sendStatus(200);

  if (alreadyProcessed(event.id)) return;

  switch (event.type) {
    case 'subscription.purchased':
    case 'subscription.renewed':
    case 'subscription.recovered':
      grantAccess(event.data.external_user_id, event.data.product_id);
      break;

    case 'subscription.expired':
      // Also sent when a full refund of the current period ends the subscription
      revokeAccess(event.data.external_user_id);
      break;

    case 'subscription.cancelled':
      // Still has access until expires_at — mark it, do not revoke
      markWillNotRenew(event.data.external_user_id, event.data.entitlement.expires_at);
      break;

    case 'identity.reconciled':
      // No external_user_id on this event. See Identity reconciled.
      repointUser(event.data.from_user_id, event.data.into_user_id);
      break;

    default:
      // Unknown type — new events can appear if you subscribed to '*'
      break;
  }

  markProcessed(event.id);
});
```

## Current limitations

<Info>
  Four gaps worth designing around. If one blocks you, tell us — they are additive
  changes we can make.
</Info>

- **No event for consumable purchases.** A consumable purchase sends no event.
  Non-consumable and non-renewing purchases send `subscription.purchased` (with
  `data.entitlement.expires_at` set to `null` for a non-consumable, and `will_renew` set to
  `false`), even though they are not subscriptions. The only payment-level event is
  `transaction.refunded`. For consumables, read
  [`GET /v1/iap/transaction-history/`](/api-reference/endpoint/get-transaction-history)
  from your server.
- **Pause, resume, auto-renew turned back on and dispute reversals do not emit events.** If you offer
  [pause](/iap/custom-cancel-flow) as a cancel-flow option, the access change reaches
  your server through no event. A customer turning auto-renew back on after cancelling
  also sends nothing: the next event is the renewal. Neither does a chargeback being
  reversed in your favour. A chargeback itself **does** arrive, as `subscription.expired`. Until this gap
  closes, re-check entitlement state on app foreground rather than treating the event
  stream as the complete picture.
- **No store resource id.** The payload does not include the Stripe subscription id or
  the Apple `original_transaction_id`. Key your records on
  `external_user_id` + `product_id`, and use
  [`GET /v1/iap/entitlements/`](/api-reference/endpoint/get-entitlements) if you need the
  underlying resource.
- **No customer email.** Not included in any event payload. Use
  [Getting Subscription Status](/iap/subscription-state) to look a customer up.
